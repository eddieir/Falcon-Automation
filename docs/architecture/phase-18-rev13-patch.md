## 7a. m-39 — every captured primitive is uncurried at module load (REPLACES rev 12 6a.1 lines 2–4 of the code block and 6a.1 item 4; AMENDS 6c.4, 6d.2, 6c.6, ADR-0044)

### 7a.1 Decision (REPLACES the rev 12 6a.1 code block)

```
"use strict";
// The first executable statements of the module, before any other require.
const uncurry = Function.prototype.bind.bind(Function.prototype.call);
const wsAdd = uncurry(WeakSet.prototype.add);
const wsHas = uncurry(WeakSet.prototype.has);
const wmGet = uncurry(WeakMap.prototype.get);
const wmSet = uncurry(WeakMap.prototype.set);
const wmHas = uncurry(WeakMap.prototype.has);
const LEDGER_REGISTRY = new WeakSet();          // never exported, never reachable
const register = (approval) => { wsAdd(LEDGER_REGISTRY, approval); return approval; };
const isLedgerApproval = Object.freeze((v) =>
    v !== null && (typeof v === "object" || typeof v === "function") && wsHas(LEDGER_REGISTRY, v));
```

1. **No captured primitive is ever invoked through a live `.call`, `.apply` or `.bind` lookup, and no captured primitive is invoked through the global `Reflect.apply`.** `WeakSetHas.call(LEDGER_REGISTRY, v)` of rev 12 is **withdrawn**: it passed `LEDGER_REGISTRY` as the first argument of a `Function.prototype.call` lookup, so a post-load hook on `.call` received the registry object itself and could then register a forged approval with the genuine `add` (SEC-12 S5). A bound exotic function is entered by `[[Call]]`; no property lookup occurs, so no hook can observe the arguments or the bound receiver (Q1–Q5).
2. **Same change applied to every captured primitive**, without exception: the gate-side capability `WeakMap` of rev 12 6d.2; `SERVER_RECORDS` and its `WeakMap` methods in `PilotFixtureServer.cjs`; the captured `net` intrinsics of rev 12 6c (`ServerAddress`, the `listening` getter, invoked as `uncurry(descriptor.get)`); the captured `EventEmitter` methods added by 7c; `crypto.timingSafeEqual`; and every `fs.promises` method captured on a hot path. An 18F static check fails on the literal substrings `.call(`, `.apply(`, `Reflect.apply(` and `.bind(` anywhere in `src/core/pilot/approval/**` and `src/core/pilot/PilotActionGate.js` other than the single `uncurry` definition line.
3. **`uncurry` is defined before any `require`.** The module's own `require` calls come after the capture block. An 18F static check asserts the capture block is the first executable statement group after `"use strict"`.
4. **Fail-closed at construction.** If any captured value is not `typeof "function"` after `uncurry`, the module throws at load (`PILOT_INTERNAL_ERROR` exit 18, reason `intrinsic_capture_failed`). Q11 shows a careless pre-load tamper produces exactly this, loudly, rather than a silent downgrade.
5. **Capture integrity assertion (extends rev 12 L16).** At first gate construction, a runtime case asserts each captured value is still functionally identical to the live native by calling it on a throwaway object, and asserts `Object.getOwnPropertyNames(capture)` is exactly `["length","name"]` and `Function.prototype.toString(capture)` matches `/native code/` (Q7).

### 7a.2 P4 is qualified; the residual class is named exactly (REPLACES rev 12 6.0 P4 and 6l item 6's scope sentence)

**What is now ruled out, with probe evidence:** post-load replacement of `Function.prototype.call`, `Function.prototype.apply`, `Function.prototype.bind`, the global `Reflect.apply`, `WeakSet.prototype.add`, `WeakSet.prototype.has`, and pollution of `Object.prototype`, `Array.prototype` and `Function.prototype`, **in any combination, cannot change the predicate's verdict, cannot leak `LEDGER_REGISTRY`, and cannot register a forged approval** (Q1–Q7). **No new owner ruling on post-load intrinsic replacement is required**, because the question is now moot: rev 12's own P4 claim and SEC-12's case L8 are satisfied for the post-load half as written.

**What remains out of scope, stated precisely and not accepted here.** Exactly one class remains: **code that executes in the Falcon process before `ApprovalStore`'s first statement.** It has three delivery routes, all of which are same-uid local code execution and all of which are already inside OWNER-10 / residual 24:
   - (a) **modification of repository code** — any module that loads before `ApprovalStore`, including a `tests/` module hoisted ahead of it (SEC-12 S7);
   - (b) **control of the Falcon process's Node command line or `NODE_OPTIONS`** — `node --require evil.cjs falcon.js`, or `NODE_OPTIONS="--require …"`. **This requires no repository change** (Q9). Rev 12 did not say so; rev 13 says so;
   - (c) **a modified Node binary or a modified `node_modules`** (residual 13, already recorded).
   **This is a disclosure, not a widening of OWNER-10.** OWNER-10's accepted class is "an author who can modify repository code, tests or workflows"; routes (b) and (c) are strictly weaker-privileged than (a) only in the sense that they touch no tracked file, and strictly equal in effect. The architecture states this rather than letting the reader infer that repository integrity alone is sufficient. **No residual is accepted here; the owner is asked to note the (b)/(c) disclosure, not to re-decide OWNER-10.**
   **No detective control is claimed.** An `execArgv`/`NODE_OPTIONS` assertion at load is **explicitly not specified as a control**, because pre-load code erases both signals and the result is byte-identical to a clean process (Q10). Proposing it would be security theatre; rev 13 refuses to.

## 7b. m-40 — what entry identity does and does not guarantee (REPLACES rev 12 6b.2 item 1's "cannot be forged" sentence and 6b.2 item 2's reliance on `falcon.js`; AMENDS 6b.3, ADR-0044, traceability item 16)

### 7b.1 The guarantee, stated honestly

1. **Guaranteed.** `require()` through Node's ordinary loader, in a process whose entry module is something else and in which `process.mainModule`/`require.main` has not been reassigned to a `Module` object for the writer's own resolved path, yields exports with **no callable member of any name** (Q12). This is deterministic under a pipe and at a real terminal alike. Rev 12 6b.2(1) is restated as **"not reachable by `require`"**, exactly as SEC-12 m-40 asked.
2. **Not guaranteed, and the rev 12 claim "object identity cannot be forged" is WITHDRAWN.** In-process code can make `IS_ENTRY` true by three routes, two of them new or sharpened relative to SEC-12:
   - `vm.compileFunction`/`vm.runInThisContext` re-evaluation of the source with a made-up `module` and `require.main` (Q13);
   - **`new Module(writerPath)` + `process.mainModule = m` + `require.cache[writerPath] = m` + `m.load(writerPath)` — Node's own loader, no `vm`, no loader patching (Q14).** This is a stronger result than SEC-12 S9 and the architecture records it as such;
   - a `Module.prototype._compile` hook **combined with** a `require.main` reassignment. The `_compile` hook **alone** does not work (Q15); SEC-12 S9's third sub-case is corrected on that point.
3. **Consequence, normative.** Entry identity is **not** a security boundary against in-process code. It is a boundary against (i) accidental in-process reachability, (ii) ordinary `require` by any shipped or test module, and (iii) `node -e` and `node --require` entry forms (SEC-12 S8). The security of the writer therefore rests **entirely** on gates that still hold when the body runs, and every one of them must be self-sufficient: `CI`/`GITHUB_ACTIONS` unset; `tty.isatty(0) && isatty(1)` by syscall; the bound eight-field prompt rendered **before** the challenge is generated; the freshly generated random challenge read from fd 0 with no parameter, option, environment key, config key or file able to supply it; and an audit entry for **every** prompt rendered, including each refusal. Reaching the body without a human still yields nothing. Reaching the body **with** a human who reads the bound prompt and types the challenge is residual 25, unchanged and not re-accepted.
4. **`approve-action.js` trusts nothing done by `falcon.js`** (SEC-12 m-40 remediation, adopted verbatim in effect). It runs, itself, in this order: `rejectKeyCarrierFlags(process.argv.slice(2))`; a **literal, closed argv allowlist** (`--approvals-root`, `--audit-root`, `--plan`, `--role`, `--origin`, `--method`, `--path`, each `--key value` or `--key=value`, no abbreviation, no negation, no repetition); and a refusal of any other token, including a bare positional. Any violation is exit 1 with the reason named, before any prompt and before any filesystem access. Verified: exit 1 on `--api-key` and on an unknown flag when the writer does the check itself (Q16). `falcon.js` keeps its own `rejectKeyCarrierFlags` at `falcon.js:477` and its own entry assertion; the two are independent and neither is load-bearing for the other.
5. **18F walker additions (normative, from m-40).** The walker fails on any of the following anywhere under `tests/`, `src/`, `scripts/` or `.github/`: a reference to `approve-action.js` by any path form; use of `vm`, `Module.wrap`, `Module.prototype._compile`, `new Module(`, `require.cache[` assignment, or `process.mainModule =`; and any write to `require.main`. Each is a **finding**, not a warning.

### 7b.2 Tests (REPLACES rev 12 6b.3 and amends 6h.1 L14)

- 9a–9c of rev 12 6b.3 stand, each still run twice (piped stdio and pty).
- **9d (new).** Direct invocation `node src/core/pilot/approval/approve-action.js --api-key X` → exit 1, reason `key_carrier_flag`, no prompt rendered, no audit entry, no ledger entry. Same for an unknown flag, a bare positional, a repeated allowlisted flag, and an abbreviated flag. Inversion: delegate the check to `falcon.js` and 9d must fail.
- **9e (new).** `new Module` + `process.mainModule` + `require.cache` seeding (Q14) and `vm` re-evaluation (Q13) are **expected-reachable** cases: the test asserts the body runs **and** that it then refuses, because stdio is piped (`approve_flag_non_interactive`) and, separately with `CI=true`, because of gate (ii). It must **not** assert that the body is unreachable. Inversion: if either sub-case ever reports the body unreachable, 7b.1(2) is stale and must be rewritten.

## 7c. m-43 — the fixture registry binds the fixture app's fixed handler identity (REPLACES rev 12 6c.4's record contents and the `isFixtureServer` contract; AMENDS AC-092)

## 7d. m-44 — `chainDeadlineMs` validates and throws (REPLACES rev 12 6i item 1; AMENDS AC-086, ADR-0042)

1. **Signature and contract.** `function chainDeadlineMs(windowMs, graceMs = 5000, absoluteMaxMs = 30000)`. Its first action asserts, for **each of the three arguments**, `typeof x === "number" && Number.isSafeInteger(x) && x >= 0`. Any failure throws `PILOT_INTERNAL_ERROR` **exit 18**, reason `invalid_chain_deadline_input`, naming the offending parameter. Only then does it return `Math.min(windowMs + graceMs, absoluteMaxMs)`. It remains pure: no clock, no config, no I/O.
2. **Why all three.** Unvalidated, `graceMs = NaN` yields `NaN` and `absoluteMaxMs = "1"` yields a **1 ms** deadline — a deadline that never expires and a deadline that always has, respectively (Q23). Validating `windowMs` alone, as SEC-12 m-44 could be read, leaves both open.
3. **Why `isSafeInteger` and not `isInteger`.** `2**53 + 1` is an integer by `Number.isInteger` but is not representable, and arithmetic on it is unsound (Q23).
4. **Fail-closed semantics.** A `NaN` deadline can never expire, so a non-finite input is not a cosmetic defect: it silently removes the chain deadline. The refusal is exit 18, never a clamp (consistent with OWNER-11 / OD-22-Q1, which forbids clamping an out-of-range configured window).
5. **Unit test rows (APPEND to rev 12 6i item 2).** Throw-rows: `NaN`, `-1`, `Infinity`, `-Infinity`, `"5"`, `""`, `null`, `undefined`, `true`, `2.5`, `[250]`, `{valueOf:()=>250}`, `2**53+1`; and `graceMs` = `NaN`, `-1`; and `absoluteMaxMs` = `"1"`. Return-rows unchanged, plus `1e9 → 30000`. All verified (Q24). Inversion: remove the assertion and every throw-row must fail with the exact unvalidated value recorded in Q23.

## 7e. m-42 — the pty helper cannot run in CI by structure (REPLACES rev 12 6g.1 wiring and 6g.2 item 2; AMENDS AC-094, AC-084 unchanged)

**OWNER-09 forbids environment-variable gating as the primary control. It is therefore specified here as defence in depth only, and the primary controls are structural.** Four layers, in the order of their strength:

1. **Primary 1 — not present on any CI-reachable path (structural).** `tests/pilot/bin/pty-approve.cjs` and `tests/regression/pilot/approval-interactive-path.test.js` live under `tests/pilot/manual/**`. That directory is excluded from every `testMatch`/`testDir` of every Playwright project and npm script that `.github/workflows/ci.yml` can reach, is listed in `.npmignore`/`files`, and is the **only** location from which the helper is resolvable. There is no copy elsewhere, and an 18F static check asserts the helper exists at exactly one path.
2. **Primary 2 — the AC-084 walker fails on reachability (structural, and already a Must).** The walker is extended so that **any** transitive `require`, `import`, dynamic `require(variable)`, `spawn`/`exec` argument, npm/yarn/npx script, or workflow `run:` line that reaches `tests/pilot/manual/**` or the string `pty-approve` from any workflow is an AC-084 **failure**, by the same transitive rule that already covers the approve flag. This is the control: it runs **in CI**, it fails the build, and it does not depend on anything the helper itself does.
3. **Primary 3 — the helper refuses any approvals root it did not observe being created (structural).** The helper requires its `--approvals-root` and `--audit-root` arguments to resolve, by `realpath`, under a directory it created itself in this process beneath `os.realpathSync(os.tmpdir())`, and refuses any path inside the repository, inside `run/`, inside `data/`, or anywhere else. So even if it ran, it could not touch real approval state. (Per SEC-12 m-42's second bullet.)
4. **Defence in depth only — `CI` detection, before the strip.** The helper's **first** executable statement, before it builds the child environment allowlist and therefore before `CI`/`GITHUB_*` are stripped, inspects **its own** `process.env` and throws if any of `CI`, `GITHUB_ACTIONS`, `GITHUB_RUN_ID`, `GITHUB_WORKFLOW`, `CONTINUOUS_INTEGRATION`, `BUILD_ID` or `TF_BUILD` is set to any value. Reason: `pty_helper_refused_in_ci`. **This is explicitly labelled defence in depth, not a control, per OWNER-09**, because it is an environment check and because an actor who can edit the helper can delete it (OWNER-10). It is specified because it converts an accident into a loud failure.
5. **The CI case (SEC-12 m-42 bullet 4).** A deterministic CI test requires the helper with `CI=true` and asserts it throws `pty_helper_refused_in_ci`. **This test must not itself be the justification for layer 4 being sufficient**, and the test file carries that comment. Inversions: move the helper to a CI-reachable path → the AC-084 walker must fail; add a workflow `run:` line naming it → the walker must fail; point the helper at the repository's approvals root → layer 3 must refuse; remove the first-statement check → the CI case must fail.
6. **R-9 is escalated from awareness to an owner confirmation**, per SEC-12 m-42's R-9 paragraph. The positive half of AC-094 is automated but not CI-gated, so regressions in the production interactive path are caught only by a manual run. Whether that meets the owner's intent ("automation of the production path, not a second mechanism") is an owner confirmation. **The architecture does not propose amending AC-084 and does not choose.**

### 7g.2 Rules, restated as detection (REPLACES rev 12 6j.1 rules 1–7)

1. *(deleted — no ENFORCEABLE class exists.)*
2. **OBSERVE_ONLY → detection, never prevention.** When a hop of an OBSERVE_ONLY class is observed on a protected attempt, Falcon **records a post-send incident**: the attempt fails the step, the run fails, the incident is audited with the observed hop class, method, origin and canonical path, and the page is torn down. **Falcon makes no claim that the hop was prevented**, and `docs/pilot/limitations.md` states, in mandatory wording: *"The hop had already been sent when Falcon saw it. 4. **The manifest, not observation, is the prevention point.** A protected non-GET is armed only on a route the manifest declares **non-redirecting**. Any observed 3xx on such a route is a manifest violation and a rule-2 post-send incident. This replaces rev 12 rule 4's unimplementable clause, and it is the only prevention rev 13 claims: it is enforced before the request is issued, from declared data, not from observation.
5. **Direct, non-redirecting protected requests remain available**, unchanged.
6. **The loopback fixture path is unaffected** (the fixture endpoint does not redirect), so AC-051's approved half still demonstrates the capability.

8. **`serviceWorkers: 'block'` is mandatory in every pilot context.** With workers allowed, a controlling service worker follows the redirect internally and the route handler sees only the first request, while the server received both hops (SPIKE-R part 2 Q1). ### 7g.3 Candidate mechanism **M1** (NEW; CANDIDATE, not a decision)

> **Superseded and deferred by owner decision OWNER-12 (Option C):** no protected non-GET request reaches this mechanism in Phase 18; the text below is preserved unchanged as an input to the deferred item 18P-PROTECTED-NONGET and is not a Phase 18 requirement. See rev 16 sections 10a and 10b.

**Statement of the mechanism as measured.** *Falcon performs the single approved request itself, with no redirect following, and returns a sanitized non-redirect response to the page.* Concretely, in the route handler at **hop 0** of a protected attempt: perform the request with redirects disabled; if the response status is 3xx, **discard it** and fulfil the page's request with `204 No Content` and no `Location`; otherwise fulfil with the response as received. No hop after 0 is ever performed, replayed, reconstructed or followed.

**Measured result.** 16 of 16 sanitized cells: **exactly one server transmission** of the protected request and **no landing request**; the page observed 204; `Cookie`, `Origin`, `Referer`, a custom CSRF-style header, `content-type` and the form/JSON body were present on that single transmission only (Q25).

**M1 is a CANDIDATE for subresource `fetch`/`XHR` only, with `serviceWorkers: 'block'` mandatory.** It is not adopted by rev 13, because it requires a Security ruling and an owner scope decision (below).

**Blocking soundness problem, flagged.** The mechanism SPIKE-R measured **is `route.fetch({maxRedirects: 0})` followed by `route.fulfill`** — the exact call that **rev 12 6j.1(7) withdrew as a shipped implementation**. M1 therefore cannot ship without amending 6j.1(7). Rev 13 proposes the following narrowed restatement and **asks Security to rule**, rather than amending it unilaterally:

> **6j.1(7), proposed amendment.** `route.fetch({maxRedirects: 0})` remains **withdrawn** as a means of reconstructing, replaying, emulating or continuing a redirect chain, and its result remains **never** evidence about browser-followed redirect behaviour. It is permitted **solely** as the performer of the single approved hop-0 request under M1, where its response is either passed through unchanged (non-3xx) or discarded entirely (3xx), and where no subsequent hop is performed.

**Why M1 is argued not to be "emulation" (rev 11's prohibition), and the residual differences.** Rev 11 forbade emulating the chain. M1 does not follow, reconstruct or synthesise any hop: it terminates at hop 0 and the chain never exists. The page is told `204`, which is the truthful statement "no content was returned", not a fabricated representation of a landing page. **Residual differences from a browser-followed request, each of which Security must weigh:**
   - the request is issued by Playwright's fetch stack, not by the renderer's network stack. Header ordering, `Accept`, `Sec-Fetch-*`, `Accept-Encoding`, HTTP version, connection reuse and TLS parameters may differ. Header/cookie **fidelity** was observed good on the fields measured [**WITHDRAWN (rev 14 section 8a.3):** SEC-13 probe T7 shows fidelity is not good for a cross-site request and the cookie divergence is not safer: M1 attached a cookie the browser withheld under SameSite, sent no Sec-Fetch headers and bypassed the CORS preflight.], but fidelity was **not exhaustively compared** against the browser's own request;
   - the page's `fetch` resolves with a 204 rather than the application's intended response, so an application that branches on the response may behave differently than it would in production — a **behavioural divergence** the pilot must disclose;
   - cookie-jar side effects of the 3xx response (`Set-Cookie` on the discarded response) are not applied to the context, a divergence in the opposite, safer direction [**WITHDRAWN (rev 14 section 8a.3):** SEC-13 probe T7 shows fidelity is not good for a cross-site request and the cookie divergence is not safer: M1 attached a cookie the browser withheld under SameSite, sent no Sec-Fetch headers and bypassed the CORS preflight.];
   - **not measured at all:** 302; top-level navigation; form-submit trigger; multipart and large bodies; `Firefox`/`WebKit`; H-7 socket retry.

**What M1 does NOT cover (normative exclusion list).**
   - **Top-level navigation.** A 204 **aborts** the navigation; it does not police it. A protected action dispatched by a navigation, including a POST-redirect-GET form submit, is **outside M1**. M1 was measured only with a `page.evaluate(fetch)` trigger.
   - **Multipart and very large bodies** (not measured; buffering and `Content-Length` behaviour unknown).
   - **Header and cookie fidelity versus the browser's own request** (partially measured, not exhaustively compared).
   - **H-7**, a Chromium socket-retry resend of a non-idempotent request below the route layer (UNVERIFIED; if unobservable it is a duplicate-transmission residual that M1 does not bound).
   - **Firefox and WebKit** (OD-19 already restricts Phase 18 to Chromium).
   - **302** (absent from the M1 cells; measured only in part 1).
   - **Service-worker message-port fetches** and `route` re-registration races (part 2 "not covered").

### 7g.4 R-7 — smallest safe scope options, presented and **NOT chosen** (NEW; input to the owner item)

> **Superseded and deferred by owner decision OWNER-12 (Option C):** no protected non-GET request reaches this mechanism in Phase 18; the text below is preserved unchanged as an input to the deferred item 18P-PROTECTED-NONGET and is not a Phase 18 requirement. See rev 16 sections 10a and 10b.

R-7 is an OWNER item. Rev 13 presents three bounded options with their consequences and selects none.

**Option A — ship protected non-GET for subresource `fetch`/`XHR` only, via M1.**
   - *Scope:* M1 applies at hop 0 of every protected non-GET dispatched as a subresource `fetch`/`XHR`, with `serviceWorkers:'block'` mandatory and the manifest's non-redirecting declaration required (7g.2 rule 4). A **navigation-triggered** protected action is **refused before arming** (`POLICY_PROTECTED_NAVIGATION_UNSUPPORTED`, exit 18).
   - *Gains:* exactly one transmission in 16/16 measured cells; no landing hop; no cross-origin body leak in those cells.
   - *Costs:* depends on the 6j.1(7) amendment and on Security accepting M1 as non-emulation; 302, navigation, multipart, form submit, header fidelity and H-7 remain uncovered; the page sees 204, a disclosed behavioural divergence; protected actions that any application dispatches by navigation are simply unavailable.
   - *Preconditions:* Security ruling on M1 and on 6j.1(7); SPIKE-R extension to cover 302 and the form-submit trigger; `docs/pilot/limitations.md` text.

**Option B — Option A, additionally allowing navigation-triggered protected actions only when every one of the following holds.** Presented as a conditional, with the conditions named so the owner can judge, not as a recommendation: (i) the manifest declares the target route non-redirecting **and** the route is same-origin; (ii) the run is in sequential mode with a single page and no concurrent arming lease; (iii) Falcon observes the navigation response and **any** 3xx aborts the run as a post-send incident; (iv) the limitation text states plainly that for a navigation Falcon has **no** pre-send control and that a 307/308 body would already have reached the next hop. *Consequence:* Option B buys navigation coverage at the cost of accepting an **unprevented** cross-origin body transmission on a manifest violation — detection only. It also leaves PRG form submits looking identical to the policed case until after the fact.

**Option C — no protected non-GET in Phase 18.** Protected non-GET actions are refused before arming for every hop class and every trigger; only read, assert and non-protected permitted actions run against authenticated pages; the loopback fixture path still demonstrates the approval capability (AC-051). *Consequence:* zero new residual from redirects, no dependency on M1, no 6j.1(7) amendment, no SPIKE-R extension; the feature's destructive-action half ships in a later phase.

**The architecture does not choose. Each option is implementable as specified. Security should judge M1 and 6j.1(7); the owner then selects the scope.**

--- APPEND to section 2 as new subsection 2b ---
### 2b. The two real execution shapes, and what pilot mode does in each

Rev 2 and rev 3 assumed a coordinator that spawns workers. The code has no such thing. Pilot mode is specified against the two shapes that exist:

**Shape 1 — one process (default run, and `--workers=N`).** `N` "workers" are bounded async tasks in one process over several `BrowserContext`s (`ParallelSweep.runBounded`). Consequences, all of which simplify the design:
- **One `EvidenceBoundary` per process, shared by every context.** The registry is a module-level singleton keyed by the active run and is *not* per-context: a value learned in context 3 is immediately known to every sink in the process. The rev 3 "worker-local registry + blinded union" problem does not exist in this shape. `attestation()` is retained for merge-time refusal only (below).
- **One run-token claim per process** (D-3 below). There are no worker claims and no claim receipts.
- **One ledger-lock holder per process**, with in-process serialisation under it (D-1(iii) below).
- Per-context state remains per-context: the arming lease, the gated-page `WeakSet` membership, auth state.

**Shape 2 — shard mode (`--shard=i/N --run-id=…`) plus a separate merge invocation.** Independent processes started by CI, with no parent, no shared memory and no inherited per-run secret. **Decision: pilot mode refuses shard mode.** `PilotLifecycle` refuses at start when `parallel.shard !== null`, and `ShardMerge` refuses any bundle carrying a `boundaryAttestation`, both `PILOT_INTERNAL_ERROR` (exit 18, reason `shard_mode_unsupported_for_pilot`). Rationale: every cross-process pilot control would need a per-run secret with no transport (the `registryKey` HMAC union, the batch nonce, the claim receipt); the only available transport is a CI secret shared by all three shards, which converts a per-run secret into a long-lived one and still cannot bind a shard to a run. Refusing is the fail-closed direction and costs no accepted criterion: AC-021/AC-051 require parity "under workers", which Shape 1 provides in full (8-context concurrency is tested, `neg-d1-lock` case (h)). **OWNER DECISION (OD-23):** confirm that authenticated pilots are not required in shard mode; if they are, a CI-secret-based `registryKey`/approval-root design must be commissioned separately and re-reviewed. Negative test `neg-pm-shard-refused` (U/R): `--shard=1/3 --run-id=… --pilot-manifest=…` refuses exit 18 with zero target requests and no file under `run/`; a bundle with a `boundaryAttestation` is refused by merge; a non-pilot shard run is byte-identical to `2572e73` (AC-076).

**No surface lets a process declare itself a worker (D-3).** There is no `--pilot-worker`, no `PILOT_WORKER`, no `PILOT_RUN_ID`, no claim-receipt path flag or env key anywhere in the design, and the pilot `runId` lives in a namespace disjoint from Phase 16's `--run-id` (which `Args.js:78` admits only together with `--shard`, which pilot mode refuses). A second process presenting a valid token therefore cannot be a "worker": it must claim `runtokens/used/<runId>` itself, which already exists, so it refuses `APPROVAL_RUN_TOKEN_INVALID`.

B. L01 — runtime registration (closes E4, SEC-04 L01 i–iv)

--- REPLACE the rev 3 "Barriers and flush semantics" item 1 (settle) ---
1. **`settle()` triggers a fresh pass, then awaits it.** `await EvidenceBoundary.settle(boundary)` is not an await on whatever happened to be in flight. It (a) awaits any diff pass already running, (b) **starts a new pass** over the cookie jar and over every page and frame (below), (c) awaits that new pass and every pending JSON-body parse, (d) resolves only when the registry version is strictly newer than the version at call entry or the pass found nothing. Two concurrent `settle()` calls coalesce onto the same *new* pass (never onto a pass started before the earlier caller's entry). Budget 2000 ms for the whole sequence; exceeding it, or a rejection inside it, is `PILOT_INTERNAL_ERROR` (exit 18) and nothing is written (E01). Every async sink calls it as its first statement, before sanitisation.

--- REPLACE the rev 3 "Barrier points" paragraph ---
**Barrier points and storage enumeration (L01 ii).** A pass runs: after every navigation commit and `load`, on every `frameattached`/`framenavigated`, after every `gate.perform` (before `settleLease` returns), on every `response` carrying `Set-Cookie`, inside every `settle()`, and at run end. A pass does, per pilot context:

- `context.cookies()` for the whole jar (context-level, all origins) and a diff against the previous snapshot.
- **Per page and per frame**, not per context: for each `page` of `context.pages()` and each `frame` of `page.frames()`, one bounded privileged evaluation (never through the `DryRunGuard` proxy) returning `localStorage` **and** `sessionStorage` entries for that frame's origin. Both are per-origin and `sessionStorage` is additionally per-tab, so a cross-origin iframe and a second page each have storage that a context-level or top-frame-only read cannot see.
- Bounds: ≤ 64 frames per page, ≤ 256 keys per store per frame, values truncated at 8 KiB, values of ≥ 4 bytes registered, keys registered when the key itself is token-shaped, under the existing 512-values-per-run cap.
- Exceeding any bound sets `storageUnscanned: true`, which in execute mode refuses the run (`PILOT_INTERNAL_ERROR`, exit 18) and in dry-run mode forbids writing any page-derived artifact. It is never a silent partial scan.
- A frame whose storage access throws (opaque origin: `about:blank`, `data:`, sandboxed) increments `inaccessibleFrames` and is non-fatal — such a frame has no same-origin store the application could have written a token into, but this is a **documented residual**, not a proof.

--- APPEND to section 10, new paragraph (L01 iii) ---
**Pilot-mode crash handlers emit codes only (L01 iii).** Node's default `uncaughtException` handler prints the message and stack to stderr, which is exactly the free-text channel section 10 otherwise eliminates: an exception whose message embeds a response body, a storage value or a cookie would bypass the boundary at the last instant. In pilot mode `PilotLifecycle`, immediately after boundary initialisation and **before** any context is created, installs `process.on("uncaughtException")` and `process.on("unhandledRejection")` (installing a listener is what suppresses the default print). Each handler:
1. writes exactly one `EvidenceBoundary.logCoded(boundary, { code: "PILOT_INTERNAL_ERROR", fields: { phase, errorClass, stackDigest } })`, where `errorClass` is admitted only from an allow-list of built-in constructor names (`Error`, `TypeError`, `RangeError`, `SyntaxError`, `AggregateError`, `DOMException`, `TimeoutError`, else `"Other"`) and `stackDigest` is `sha256(stack)` hex — **never the message, never the stack, never `err.cause`, never a Playwright error call log**;
2. runs `PilotLifecycle.cleanupAll()` under a 5000 ms cap (which ends with a final `settle()` then `await Logger.flush()`), swallowing any secondary throw;
3. `process.exit(18)` in a `finally`, so a throw inside the handler cannot fall back to Node's printer.
The handlers are removed on normal teardown so non-pilot runs in the same process are unaffected. Negative test `neg-l01-uncaught` (U/R): a pilot run in which a route handler throws an `Error` whose message and whose `cause` each contain a registered canary — captured stdout and stderr contain zero canary bytes in every derived form, exactly one `PILOT_INTERNAL_ERROR` line is emitted, exit is 18, `cleanupAll` is observed to have run, and `reports/execution.log` after `flush()` holds zero canaries. Inversion: with the handlers removed the canary appears on stderr.

--- REPLACE the rev 3 "Worker registries and shard merge (L01)" block in full (L01 iv) ---
**One registry per process; merge refuses pilot bundles (L01 iv).** Per section 2b the only supported parallel shape is in-process, so there is one boundary and one complete registry per process and the rev 3 cross-process union is unnecessary. Two rules remain:
- **Attestation is a merge-time refusal, not a union.** `ShardMerge` refuses any bundle that carries a `boundaryAttestation { registrySize, derivedForms, assertCleanCount, settleCount, mode }` at all (shard pilots are refused, so such a bundle can only come from an unsupported or tampered build) and refuses any bundle lacking one if the merge was invoked with a pilot manifest. `PILOT_INTERNAL_ERROR`, nothing merged.
- **`attestation()` is retained** as a self-check asserted by a unit test (`assertCleanCount > 0`, `settleCount > 0`, `mode` matches the run mode) and is written only into the in-process run report, never into a bundle. `secretIndex` and `registryKey` are **removed from the design**; the run token is still never registered anywhere a second process could read it.
Residual removed by this change: the rev 3 "undelimited secret embedding in shards" residual no longer applies (no shard pilots). Residual retained: nothing cross-process is scanned, because nothing cross-process is produced.

C. D-1 — ledger lock (closes E3)
=====================================================================

--- REPLACE the `lockExclusive` bullet in section 2a (rev 3 patch line 37) in full ---
- `lockExclusive(lockPath, { timeoutMs = 5000, staleMs = 60000 })` — **D-1.** Two levels, because a process cannot acquire its own `O_EXCL` file twice:

  **Level 1 — process-wide FIFO queue.** A module-level async queue keyed by `lockPath` serialises every acquisition attempt in this process. The queue head alone touches the filesystem; siblings wait in memory, so 8 in-process contexts appending concurrently never spin on `EEXIST` against themselves.

  **Level 2 — the `O_EXCL` holder record.** The queue head creates `lockPath` with `open(…,"wx",0o600)` containing `{ nonce, pid, startedAtIso, hostname, bootId, bootIdSource }` where `nonce` is 128 random bits, then `fh.sync()` + directory `fsync`.

  **Reentrancy is dynamic-extent only (D-1 iii).** An `AsyncLocalStorage` store created by `run()` at acquisition carries the handle. A nested acquisition is a no-op **only when `als.getStore()` already holds a handle for this `lockPath`**, i.e. only for callbacks that are descendants of the acquiring call — which is exactly the `consume` → audit-append case. It is not keyed by run, pid or context, so a *sibling* in-process append has no store, falls to the level-1 queue and waits. Asserted by test, both directions.

  **Staleness (D-1 ii).** A holder record is a candidate for breaking only when **all** of: `hostname === os.hostname()`; the record is older than `staleMs`; and either the recorded `bootId` differs from this boot's (a different boot means every PID from the old boot is dead) or `process.kill(pid, 0)` throws `ESRCH`. `EPERM` from `process.kill` (live foreign-uid process) is never stale — refuse. **A record whose `hostname` differs is never broken and never waited out: refuse immediately** `PILOT_INTERNAL_ERROR` (exit 18, reason `lock_foreign_host`) — with `assertLocalFilesystem` in force this should be unreachable, so reaching it means an assumption broke. `bootId` is `/proc/sys/kernel/random/boot_id` when readable (`bootIdSource: "procfs"`), otherwise a one-minute-bucketed boot epoch `floor((Date.now()/1000 - os.uptime())/60)` (`bootIdSource: "uptime"`); when either side is `"uptime"`, "differs" means differs by more than 2 buckets, so a clock step is not read as a reboot. No sysctl child process is spawned per lock; no OS behaviour beyond `os.uptime()`/`os.hostname()` is claimed. The bucket source is an injectable seam for tests.

  **Breaking, under an `O_EXCL` guard with identity verification (D-1 i).** Rev 3's rename-aside alone is racy: two breakers can both judge the same record stale, A renames it aside and creates a live lock, then B renames A's *live* lock aside. Corrected protocol, in order:
  1. `lstat` + read the holder record; record `{ nonce, dev, ino }`; judge staleness as above.
  2. `SafeFs.createExclusive(lockPath + ".break", { breakerPid, targetNonce, at })`. `EEXIST` means another breaker owns the critical section: do **not** break; back off with jitter and retry acquisition. A `.break` guard older than `2 × staleMs` is itself renamed aside (same identity protocol, recursion depth 1) before retrying.
  3. Inside the guard, **re-read `lockPath`**. If it is absent, or its `nonce`/`dev`/`ino` differ from step 1, the lock changed under us: abort the break, unlink the guard, retry acquisition. This is the check that makes the double-break impossible — B's step 3 sees A's new nonce.
  4. `rename(lockPath, lockPath + ".stale." + targetNonce)`, then **verify the renamed file's identity**: `lstat` it and read it back; its `nonce` must equal `targetNonce` and its `dev`/`ino` must equal step 1's. If not, the rename captured a file we never judged: refuse the run `PILOT_INTERNAL_ERROR` (exit 18, reason `lock_break_identity_mismatch`) and attempt no restore and no acquisition — fail closed, leave the evidence in place.
  5. Unlink the guard; attempt a normal level-2 create.

  **The holder re-checks before commit (D-1 i).** `unlock(handle)` already re-`lstat`s and compares content before unlinking. Additionally, **every write under the lock re-reads `lockPath` and compares `nonce`, `dev` and `ino` with the handle immediately before the first `fsync` of the commit sequence** (the `consume-intent` append in section 9 step 1, each seal, each anchor append, each `approvals.json` rewrite). A mismatch means this process lost a break race while believing it held the lock: abort the write before it is durable, `PILOT_INTERNAL_ERROR` exit 18, zero clicks. Timeout → `{ok:false, code:"LOCK_TIMEOUT"}` → exit 18, never a lock-free fallback.

--- APPEND cases to `neg-d1-lock` (section 9 ledger-write-lock paragraph) ---
(f) **Two simultaneous breakers:** a stale record is planted, two processes are released at the same barrier; exactly one creates `lockPath`, exactly one `.stale.<nonce>` file exists, the surviving holder's nonce is its own, and a subsequent `verify()` passes. Inversion: with step 3's identity re-check removed, a live lock is renamed aside and the test fails.
(g) **PID reuse with a different bootId:** a record naming a *live* PID of this host, older than `staleMs`, with a `bootId` two-or-more buckets away, is broken and the run proceeds; the same record with the current `bootId` is **not** broken (exit 18). (h) **Contiguous chain at both scales:** 8 in-process contexts consuming 8 distinct approvals in one process, plus 8 separate processes consuming 8 more, produce 16 well-formed entries with globally contiguous `seq`, one holder at a time, and `verify()` passes. (i) **Reentrancy scope:** an append nested inside `consume`'s dynamic extent is admitted without a second file acquisition; a sibling task's append started from outside that extent waits on the queue. --- REPLACE the rev 3 "Claim once, by the coordinator (D-3)" bullet in full ---
- **Claim once, per process (D-3).** `runtokens/used/<runId>` is created with `createExclusive` exactly once, by **the process that will dispatch** — the single process of Shape 1 — at run start, before any protected action and before any context is created. In-process workers do not claim: they share the process's claim, because they share the process. Per-action exclusivity remains the per-`approvalId` consume marker under the ledger lock, so two in-process tasks racing the same action yield exactly one dispatch. Protected actions in shard mode are unreachable (section 2b refuses the run before the store is opened). E. N-3 — SPIKE-W made preventive, and a route.fetch body cap (closes the P1 candidate)
=====================================================================

--- REPLACE the rev 3 "Dedicated Web Workers (N-3). SPIKE-W" bullet in full ---
- **Dedicated and shared workers (N-3), preventive first.** Rev 3's `page.on("worker")` refusal is a race: the worker can issue a `fetch` synchronously at the top of its script, before the event is delivered and the context torn down; `Blob`/`data:`-URL worker scripts are not fetched over the network at all, so route-based script denial does not see them; and `SharedWorker` coverage is unverified. **Decision: prevention in the page, with the event as a backstop.**
  1. **Preventive (`addInitScript`, installed before any navigation on every pilot context, execute mode).** The script, in a non-leaking IIFE, redefines `Worker` and `SharedWorker` on `globalThis` (and on `self` for nested scopes it can reach) as non-configurable, non-writable constructors that unconditionally `throw new DOMException("…","NotSupportedError")`, and leaves `navigator.serviceWorker` to the existing `serviceWorkers: "block"`. A worker therefore never starts, so there is no script to race: the `Blob`-URL and `data:`-URL bypasses are closed by the same change, because the bypass is in the script *source*, not the constructor. The script also records a page-side counter the gate reads, so a construction attempt is observable.
  2. **Backstop (`page.on("worker")`).** If a worker nonetheless exists (a browser-internal path, a future Playwright change, or a page that obtained a pristine constructor from an iframe Falcon did not init), the run refuses `PILOT_INTERNAL_ERROR` (exit 18, reason `worker_not_interceptable`) immediately. The backstop is a detector of a broken assumption, never the primary control.
  3. **SPIKE-W is retained, with its scope changed.** It no longer decides whether to ship a control; it records (a) whether worker-initiated requests are observed by `route` on the pinned Playwright version — if they are, the preventive script remains anyway and the interception is defence in depth — and (b) whether the preventive script survives every frame-creation path the fixture can build (`srcdoc`, `about:blank`, `data:` iframes, `document.write`). Any path where it does not is documented in `docs/pilot/limitations.md` and, in execute mode, each such frame type is refused at `frameattached` rather than relied upon. No Playwright or Chromium behaviour is asserted here.
  Negative test `neg-n1-worker-fetch` (rewritten): a fixture page whose **worker POSTs synchronously as its first statement** — the `new Worker(…)` call throws, the fixture mutation counter is 0, the run continues (construction alone is not a refusal; it is a counted denial) and the attempt is recorded; the same case with a `Blob`-URL script and with a `data:`-URL script; the same case with `SharedWorker`; **each repeated 50 times in one run with the counter asserted 0 on every repetition** (the repetition is what would surface a race). Plus `neg-n1-worker-backstop`: with the preventive script disabled, the backstop fires exit 18 — and the 50-repetition POST counter is asserted to be *non-zero* in that configuration, which is the recorded evidence that the event alone is a race and the prevention is load-bearing.

--- APPEND to section 7a item 5 (redirect fallback), new sub-bullet ---
- **`route.fetch` response-size bound (N-3).** `route.fetch` buffers the whole response in the Node process, so an unbounded or attacker-chosen body is a memory-exhaustion vector in the very mode that is supposed to be the safest. In a pilot context the fallback path refuses to buffer more than **8 MiB** per response: the request is dispatched with `route.fetch`, and the response is rejected when `content-length` exceeds the cap, or — because `content-length` may be absent or false — when the delivered body exceeds the cap (`POLICY_NETWORK_BLOCKED`, reason `response_too_large`, exit 13, request aborted, nothing fulfilled). A total per-run buffered-bytes budget of 256 MiB is enforced the same way. Streaming is *not* claimed to be available on the pinned version; if SPIKE-R finds a streaming API that preserves the per-hop checks, 18C may use it, and the cap then applies to the streamed total. Negative test `neg-n3-fetch-cap`: a fixture route returning 9 MiB with a correct `content-length`, one returning 9 MiB with no `content-length`, and one returning 9 MiB with a lying `content-length: 10` — each aborted `response_too_large`, process RSS growth bounded, mutation counter 0.

F. N-2 — bind the lease to the page/frame, and state the body residual
=====================================================================

--- REPLACE the rev 3 "Arming window" bounding rules list in section 9 ---
Bounding rules, so the window is not a general permit:
- **Bound to the gated page and frame (N-2).** `arm(ctx, approvedAction, { windowMs, page, frame })` records the page and the frame in which the approved control was verified at step 11. A request consumes the lease only when `request.frame()` is non-null, `request.frame().page() === lease.page`, and `request.frame() === lease.frame` or a descendant frame of it. A request from another page in the same context, from an unrelated frame, or with no frame at all (context-level `APIRequestContext`, a worker, a service worker, a browser-internal fetch) **never** consumes the lease and is judged as if nothing were armed. Rev 3's "any page in the context, or any script, can consume the triple" is closed by this.
- **Bound to the request shape (N-2).** In addition to the exact `{method, serialised origin, canonical path}` triple: `request.resourceType()` must be in the approved action's declared set (`document`, `xhr`, `fetch`), `request.postDataBuffer()` length must be ≤ 1 MiB, and the `content-type` must be in the declared set. When the plan records an expected body (an API-shaped approved action), the lease additionally carries `bodyDigest = Digest.digest("action-v1", { sha256 })` and a mismatch aborts.
- **Residual, stated honestly: for a UI-dispatched action the body contents are not approved.** The body of a form or SPA POST is generated by the page after the click, so it is unknown when the lease is minted and there is nothing to bind it to. --- APPEND to section 9, new paragraph before the crash-window table (D-a) ---
**Torn tail is physically truncated under the lock (D-a).** A segment whose last line is incomplete (no terminating newline, or a line that is not parseable `JsonStrict` JSON, or a line whose recorded per-entry hash does not match its body) is a crashed append, not tampering — but leaving it in place reintroduces P02's permanent denial of service, because every later `verify()` would read a malformed chain. Under the ledger lock, before the first append of a session and before every seal, the appender: locates the last byte offset at which the segment is well formed; if that is not the file size, **physically truncates** the file to that offset with `fh.truncate(offset)` + `fh.sync()` + directory `fsync`; and records the discarded byte count as a field `priorTailTruncatedBytes` on the **next** entry it appends (no new entry type and no new code). **`anchors.log` genesis protocol (D-c).** D-4 makes a missing `anchors.log` `APPROVAL_HISTORY_TAMPERED`, which would turn a crash during first initialisation into a permanently unusable store.

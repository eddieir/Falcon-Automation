--- APPEND a new subsection after section 2b rule 6, "2b.1 Pilot bundle contents are a closed five-shape set (closes M-1, M-2)" ---

**(a) Admitted journal event types in pilot mode (M-1, AC-022/AC-067, OD-17).** `Schemas.js:14-17` admits eight event types. `ShardMerge.js:325-354` applies six of them to `healing_pending.json`, `locator_store.json` and `locator_memory.json`, and `ci.yml:475-493` caches `healing_pending.json` on main, so a journal is a transport for exactly the application-derived identity OD-17 excludes. Rule 3(d)'s key-and-filename check does not stop it. Decision:

1. A pilot journal admits **only** `flakiness.outcome` and `task.end`. The six types `healing.pending`, `healing.tier3`, `healing.log`, `locatorStore.use`, `locatorMemory.evidence` and `locatorMemory.candidate` are **excluded by type**, structurally, in both directions:
   - **write side:** the pilot journal builder emits only the two admitted types, and `ShardBundle.put` refuses a journal carrying any other type (`BUNDLE_EXCLUDED_TYPE`, run refused, bundle directory removed);
   - **read side:** a pilot merge refuses a bundle whose journal carries any other type (`BUNDLE_EXCLUDED_TYPE`, exit 2) **before** any reducer runs. This is a type check on the validated journal, not a string scan.
2. A pilot merge **runs no healing and no locator reducer**. The three steps `healing_pending`, `locator_store` and `locator_memory` are not executed: no `Reducers.reduceHealingPending`, no `Reducers.reduceLocatorStore`, no `LocatorMemory.applyMerge`, no `Reducers.buildHealingLog`. `scenario_history` and `quarantine_decisions` still run, because `Reducers.reduceFlakiness` (`Reducers.js:141`) consumes only `flakiness.outcome` and carries no identity.
3. **The merged report stays correct.** Test rows, `uiIssues` and each page's status come from fragments (`ShardMerge.js:174-177`), coverage comes from the page table, and `ReportManager.buildReport` derives `report.result` from test rows only (`ReportManager.js:195`) — none of these reads an excluded event. The only differences in a pilot merge are: `healingEvents` and `reports/healing_logs.json` are `[]`; the three stores are untouched; and `buildRunRecord`'s `pendingDepth` is taken from the **freshly read** `healing_pending.json` key count rather than from a reducer result, so run history stays consistent with the unchanged store.
4. **Post-condition, asserted not assumed.** The pilot merge digests `healing_pending.json`, `locator_store.json` and `locator_memory.json` before step 3 and re-digests them after step 5; any difference is a safety-invariant violation, exit **17**, `PILOT_STORE_MUTATION`, and the receipt records it. This is a backstop for 2, not a substitute.
5. **The rev 5 rule 3(b) reduced healing record `{strategyId, outcome, locatorKeyDigest}` is DROPPED.** It is healing evidence, and OD-17 excludes healing evidence; `locatorKeyDigest` is additionally a digest of application-derived identity and therefore a confirmation oracle on element identity. Pilot runs record healing only in process-local logs that never enter a bundle.

**OD-17-Q1 (OWNER DECISION, not accepted here).** Keeping any pilot-mode healing record in a bundle — even the reduced one — requires the owner to amend OD-17. The design assumes **no**: pilot bundles carry no healing evidence, and pilot runs get no cross-shard healing or locator learning. Cost: a pilot shard run contributes nothing to `healing_pending.json`, `locator_store.json` or `locator_memory.json`, so authenticated pages do not improve locator memory. Benefit: no application-derived identity crosses a process boundary and the `ci.yml:475-493` state cache can never be fed from a pilot run. If the owner amends OD-17, the record returns as a sixth shape with its own closed schema and its own security review; it is not re-admitted by implementer discretion.

**(b) `timings.json` is the fifth allowlisted shape (M-2, AC-067).** SEC-05 is correct that `ShardBundle.put` is not the only bundle writer: `Runner.js:22,136` writes `timings.json` with a direct `SafeFs.writeAtomicPrivate` after the sweep returns, and `ShardMerge.js:252` reads it with `SafeFs.readBoundedJson({maxBytes:4096,maxDepth:3})` and no closed schema. **Correction to M-2's leakage path:** `readTimings` copies only `discoveryMs`, `analysisMs` and `executionMs` into the report (`ShardMerge.js:243-261`), so an extra key never reaches the merged report; the leak path is the **artifact upload at `ci.yml:412-416`**, which AC-060 covers ("every persisted artifact ... and shard runs"). The fix is still required, and for two reasons: the artifact path, and the fact that rules 2–3 as written make every pilot merge return `BUNDLE_UNEXPECTED_FILE`. Decision:

1. New closed schema `Schemas.validateTimings`: `{schema:"falcon.shard-timings", v:1, discoveryMs, analysisMs, executionMs}`, closed key set, each value a finite integer in `0..604800000`. No optional keys.
2. `Runner.js:134-136` no longer writes the file directly. It calls `ShardBundle.writeTimings(bundleDir, timings)`, which validates, then goes through `put` — so `settle()` + `assertClean` (rule 3(a)) applies to it like every other bundle byte. A validation failure is `BUNDLE_TIMINGS_INVALID`; today's "could not write shard timings" warning behaviour on an I/O failure is unchanged.
3. The bundle allowlist is **exactly five shapes**: `manifest.json`, `timings.json`, `analysis.json`, `fragments/page-<n>.json`, `journals/page-<n>.json`. Every rev 4/rev 5 sentence reading "exactly four shapes" reads "exactly five shapes".
4. Merge side: a **pilot** merge validates `timings.json` with the closed schema and refuses a non-conforming or missing one (`BUNDLE_TIMINGS_INVALID`, exit 2), except for a refusal bundle (2b.2), where it must be absent. A **non-pilot** merge keeps today's behaviour exactly — `readTimings` returns `null` on anything invalid and the merge proceeds — so AC-076 holds byte-for-byte.
5. The writer-inventory unit test (rev 5, 18E) must enumerate `src/core/parallel/` for every call site that writes under a bundle directory and assert that `ShardBundle.put` is the only one. `Runner.js` is in its scope. This test is the standing guard against a sixth writer.

*Alternative considered and rejected: fold the three numbers into `manifest.json`'s `timing` block.* It is the cleaner end state and removes a file shape, but the manifest is written inside the sweep (`Runner.js:124`) while timings are only known after it returns (`Runner.js:134`), so folding reorders non-pilot writes and changes non-pilot manifest bytes. That widens AC-076's blast radius for no security gain once `put` is the sole writer. Revisit outside Phase 18.

--- APPEND a new subsection "2b.2 The refusal bundle (closes M-3, AC-023)" ---

SEC-05 M-3 is correct: a shard that exits 11 before or during discovery has no `frontierDigest` and no `planDigest` (each shard discovers independently, `ParallelSweep.js:73-80`), both are in `ShardMerge.COMMON` (`ShardMerge.js:35`) and compared for equality at `ShardMerge.js:124`, and `buildPageTable` refuses an assigned page with no fragment (`ShardMerge.js:148-149`). As rev 5 stands the merge returns exit 2 and the loss attribution is lost. A refusal bundle is therefore a **declared shape**, not a relaxation:

1. **Shape.** A refusal bundle contains exactly one file: `manifest.json`. Zero fragments, zero journals, no `analysis.json`, no `timings.json`; any additional file is `BUNDLE_UNEXPECTED_FILE`. Its manifest is schema-valid, carries `exit.code` 11 or 12, `pilot: {authCoverage:"lost", reason, boundaryAttestation}`, every page `assigned` as derived and `disposition:"skipped"` with `fragment:null` and `journal:null`, and a `boundaryAttestation` with `settleCount > 0` and `assertCleanCount >= 1`.
2. **Unknown-digest sentinel.** `frontierDigest` and `planDigest` are non-optional `hex64` (`Schemas.js:171-172`). A refusal bundle sets both to `"0".repeat(64)`, declared as the unknown sentinel. This needs **no schema change**. The sentinel is admitted **only** in pilot mode, **only** with `exit.code` 11 or 12, and **only** with `authCoverage:"lost"`; an intact shard presenting it, or any non-pilot bundle presenting it, is refused `SENTINEL_DIGEST_NOT_ADMITTED` (exit 2).
3. **Admission is gated, never inferred.** A merge admits a refusal bundle only when all of these hold: pilot mode; `exit.code` in {11,12}; `authCoverage:"lost"`; the single-file shape of 1; a valid `boundaryAttestation`; and `runId`, `commit` and `pilotManifestDigest` matching the merge's own expectations (these are locally derived and therefore always available, even on an exit-11 shard). Failing any of these is exit 2. **No check is relaxed for a non-refusal bundle.**
4. **Partition.** `loadManifests` partitions the shard set into `intact` (non-refusal) and `refusal`. `COMMON` equality (`ShardMerge.js:124`) and `buildPageTable` (`ShardMerge.js:132-149`) run over `intact` only. A refusal shard contributes no fragment, no journal and no event. At least one intact shard is required; with zero intact shards the merge produces a report with `pagesTestedAuthenticated: 0`, `authCoverageLost` listing every shard, `report.result !== "PASSED"` and the exit code from the rank table (11 or 12) — never exit 0 and never exit 2, so the attribution survives.
5. **Lost pages.** The page table is the union of the intact shards' pages. Every ordinal whose `shardOf` owner is a refusal shard is present in the merged report with `disposition:"skipped"` and `status:"lost"`, is counted in neither `pagesTested` nor `pagesTestedAuthenticated`, and is listed under `coverage.authCoverageLost` by shard index. `status:"lost"` is a merged-report value only; it is not added to `Schemas.PAGE_STATUSES` and the dashboard treats an unknown page status as not-tested.
6. **An incomplete set is still not a refusal bundle.** A shard that produced no directory at all remains `MISSING_SHARD` (`ShardMerge.js:126`, exit 2). A refusal bundle is how a shard *reports* its loss; its absence is still a rejected input, and neither is ever a pass.

--- APPEND a new subsection "2b.3 Total exit precedence and shard-code cross-checks (closes M-4)" ---

SEC-05 M-4 is correct: rev 5's order ranks only {2,3,12,11,14,1,0} while the additive schema widens `exit.code` to 0..3 plus 10..18, leaving 10, 13 and 15..18 undefined and able to fall through to 0. Decision:

1. **Total rank, every admitted code, no default.** `rank(code)` is a frozen table over the full admitted set, highest first, aligned with the `exitCodes` contract in `docs/phase-18-acceptance-criteria.json` (rejected input and non-durable state first, then internal/safety, then identity and policy, then auth loss and auth setup, then approval and manifest, then failed, then pass):

   `2 > 3 > 18 > 17 > 16 > 15 > 13 > 12 > 11 > 14 > 10 > 1 > 0`

   `rank()` **throws** on any integer not in this table; the thrown case is exit 2, never 0. There is no fall-through and no `default:`.
2. **Pilot shard manifests admit only {0,1,11,12,14}.** Any other code in a shard manifest — including 2, 3, 10, 13 and 15..18 — is refused `SHARD_CODE_NOT_ADMITTED` (exit 2). Codes 13 and 15..18 are therefore unreachable in a manifest; they are ranked anyway so that a merge-derived or future code can never be silently treated as a pass.
3. **Cross-check of the declared code against bundle content.** All of these are `SHARD_CODE_INCONSISTENT` (exit 2):
   - `exit.code` in {11,12} without `authCoverage:"lost"`, or `authCoverage:"lost"` with `exit.code` not in {11,12} — the equivalence is enforced in both directions;
   - `exit.code` in {11,12} with any fragment, journal, `analysis.json` or `timings.json` present (it must be the refusal shape of 2b.2);
   - `exit.code` 14 with no page carrying a refused protected step, or with `authCoverage` other than `"intact"`;
   - `exit.code` 0 together with any refused protected step, any failed row, or any `status:"lost"` page;
   - any fragment whose `authContext.mode` is `"anonymous"` in a shard declaring `exit.code` 0 — an intact shard that produced an anonymous page must declare 1, or 12 if it lost authentication mid-run.
   - a bundle with no `pilot` block in a pilot merge, or a `pilot` block in a non-pilot merge (rev 5 rule 3(d) unchanged).
4. **Interpretation of M-4's anonymous-fragment rule, for SEC-06 confirmation.** M-4 asks that "an `anonymous` fragment in an 'intact' shard is refused". A blanket refusal would also refuse a legitimately anonymous page inside an authenticated pilot (a login or marketing page the pilot manifest includes), so the design narrows it to 3's last two bullets: an anonymous fragment is admitted, is reported `status:"unauthenticated"`, is **never** counted in `pagesTestedAuthenticated`, and makes an `exit.code` of 0 inconsistent. If SEC-06 requires the blanket refusal instead, the pilot manifest needs a per-page expected-mode declaration; that is new surface and is not added speculatively.
5. **`pilot` is required on every pilot bundle manifest** (rev 5's `boundaryAttestation` requirement extends to the whole block), and a manifest code of 10 or above without a `pilot` block is refused in **both** modes — this is SEC-05 answer (iii)'s second condition.
6. **Merged code.** `mergedCode = argmax(rank)` over the merge-derived code **and every shard-declared code**. The receipt records the merge-derived code, every shard code, the winning code and the rank table version, and the receipt replay recomputes and must return the same code. An older build reading a pilot bundle still refuses it as `MANIFEST_UNKNOWN_KEY` → exit 2, which is fail-closed and ranks highest.

--- APPEND to section 2b rule 4 (closes m-6, with a code-fact correction) ---
The merge also verifies the pilot manifest it was given: it compares each bundle's `pilotManifestDigest` against the digest of its own `--pilot-manifest` and refuses a mismatch `MIXED_PILOTMANIFESTDIGEST` (exit 2), exactly as it already does for `expectRunId`/`expectCommit`. **Correction to SEC-05 m-6:** these expectation flags are not parsed in `Args.js`. `Args.js:70-88` accepts only `--input` and `--expect-total` for merge; `--expect-run-id`/`--expect-commit` are parsed by `Runner.parseMergeExpect` (`Runner.js:47-65`) and gated by `MERGE_FLAG` (`Runner.js:25`), which refuses any unknown merge flag. `--pilot-manifest` is therefore added to `MERGE_FLAG` and to `parseMergeExpect` (path validated through the strict loader, resolved and digested before use) and passed to `ShardMerge.merge({pilotManifest})`; `Args.js` is unchanged. A pilot merge without `--pilot-manifest` refuses every bundle carrying a `pilot` block (rev 5 rule 3(d)), so the flag is the mode switch and cannot be inferred from bundle content.

--- APPEND to section 7 (SPIKE-R) (closes m-10, carried SEC-04 N-3) ---
`route.fetch` has no documented pre-buffer bound, so a response-size cap enforced on the returned body is checked only **after** the body is in memory. **SPIKE-R must record explicitly whether a pre-buffer bound exists.** If it does not, the design adds both: a per-`route.fetch` timeout and a **run-level RSS ceiling** checked on a timer, whose breach is a safety-invariant refusal (exit 17) with the run torn down. Verification: a fixture route streams a **chunked** body with no `content-length`, far larger than the cap; the run refuses deterministically and RSS stays under the ceiling. Until SPIKE-R reports, this is an open condition on 18C, not a closed item.

# Phase 18 architecture — revision 5 patch (ARCH-05)

Normative addendum to the [rev 4 patch](phase-18-rev4-patch.md). It withdraws the rev 4 decision that pilot mode refuses shard mode (ADR-0038 as written there, OD-23) and replaces it with: shard mode is supported; protected actions are refused in shard mode. Each block below states what it replaces. Status: DRAFT pending the SEC-05 review; OD-23 (re-scoped) needs owner confirmation. No risk is accepted.

> **Superseded by ARCH-05 (rev 5 delta below).** The rev 4 decision that pilot mode refuses shard mode is withdrawn in full. Shard mode is a **supported** authenticated pilot shape: each shard is an independent pilot process that derives its own role state from local input, runs its own boundary registry, and enforces the identical deterministic policy. The only restriction is that **protected actions are refused in shard mode** (OD-23, re-scoped). The in-process worker model (one registry, one token claim, one lock holder per process) is unchanged and still stands.

--- REPLACE section 2b "Shape 2" paragraph in full ---
**Shape 2 — shard mode (`--shard=i/N --run-id=…`) plus a separate merge invocation.** `Args.js:77-78` requires `--shard` with `--run-id`; `ci.yml:365-420` starts `node falcon.js --shard="$i/3" --run-id="$RUN_ID"` on three independent runners, each with its own checkout and its own filesystem, and `ci.yml:421-454` merges as a fourth invocation. There is no parent, no shared memory, no shared filesystem and no inherited per-run secret. **Decision: pilot mode supports shard mode as N independent, mutually isolated pilot processes plus a verifying merge. Protected actions are the single capability refused in this shape.** Six rules make it sound; each is a reinstatement of a Shape 1 control at process scope, not a relaxation:

1. **State is local-only, never transported (AC-022, AC-067).** A shard resolves its role state exclusively through the same strict loaders Shape 1 uses: a manifest `stateFile` resolved by `SafeFs.resolveUnder(authRoot, …)` on *its own* runner, `--auth-import` through `readBoundedPrivateJson({requireMode:0o600})`, or a login from `PILOT_ROLE_*_USERNAME`/`PILOT_ROLE_*_PASSWORD` (CI secrets, `::add-mask::`-ed, per-job). The same `git check-ignore` fail-closed check, the same `0o077`-refusal on `run/auth`, the same `assertLocalFilesystem`. **No bundle, no artifact and no merge input ever carries a `storageState`, a cookie, a storage value or a token**; the loaders are the only inbound path and they read nothing produced by another shard.
2. **One `SecretRegistry`/`EvidenceBoundary` per shard process, for that shard's own artifacts only.** Each shard registers the values *it* learned and is the only writer of its own bundle. Nothing cross-process is unioned, so rev 4's deletion of `registryKey`/`secretIndex` stands unchanged (there is still no per-run secret and still no transport for one). Every byte a shard writes outside its process goes through the bundle allowlist plus `assertClean` (rule 3), so unscanned cross-process output does not exist.
3. **Bundle allowlist + `assertClean` at one choke point (AC-067, OD-17).** A pilot bundle is exactly four shapes and nothing else: `manifest.json`, `analysis.json`, `fragments/page-<n>.json`, `journals/page-<n>.json`, each already closed-key-validated (`Schemas.validateManifest` `Schemas.js:167`, `validateFragment`, `validateJournal`) with URLs normalised through `Schemas.storedUrl`/`urlId` and text through `Schemas.redactText`. Additions: (a) `ShardBundle.put` (`ShardBundle.js:79`) — the sole writer — calls `await EvidenceBoundary.settle(boundary)` then `assertClean(text)` before every `writeAtomicPrivate`, and a hit is `EVIDENCE_LEAK_DETECTED`, run refused, bundle directory removed; (b) a declared **excluded-type list** enforced structurally, not by scan: no `storageState`/`cookies`/`origins`/`localStorage`/`sessionStorage` key may exist anywhere in a pilot bundle, no locator-memory entry and no healing evidence carrying application-derived identity (selector text, attribute values, screenshots, DOM excerpts) — healing evidence in pilot shard mode is reduced to `{strategyId, outcome, locatorKeyDigest}`; (c) identity in a bundle is `{roleId, pilotManifestDigest}` only — **never** a digest of state or of any cookie value, so a bundle is not a confirmation oracle; (d) **merge re-verifies**: `ShardMerge.loadManifests` enumerates each `shard-i-of-N/` directory and refuses any file name outside the allowlist (`BUNDLE_UNEXPECTED_FILE`), refuses any manifest key outside the closed set, and refuses any excluded key at any depth. `ShardMerge` **no longer refuses pilot bundles**; it refuses *non-conforming* ones.
4. **Identical deterministic policy in every shard (18F gate).** The pilot manifest is a local file; its digest is added to `ShardMerge.COMMON` (`ShardMerge.js:35`), so a merge whose shards did not run byte-identical manifest origin/route/deny/auth-loss/budget policy is refused `MIXED_PILOTMANIFESTDIGEST` (exit 2). Each shard installs the same `NetworkGate`, the same route/origin/scheme/redirect rules, the same crash handlers, the same storage enumeration and the same `settle()` barriers. Policy is derived from the manifest in-process, never inherited, so there is nothing to propagate and nothing to tamper with in transit.
5. **Protected actions are refused in shard mode, fail-closed, at plan projection.** Rationale (answers SEC-04 D-3 and D-1 directly): an approval is a human-reviewed record in a *local* `run/approvals/` ledger whose integrity rests on an `O_EXCL` lock on a local filesystem (ADR-0035) and on a token claimed exactly once per process (D-3). Across runners there is no shared filesystem, so (i) a record minted on runner A does not exist on runner B; (ii) transporting the approvals root or the run token through a CI secret or artifact converts a per-run secret into a long-lived one shared by N runners, gives N processes one token (breaking "claim once"), forks the chain with no lock holder, and leaves `verify()` unreconstructable — rejected; (iii) "each shard claims its own token against its own approvals root with the shard identity in the digest" is rejected because that root is created by the run itself on an ephemeral runner, so the approval would be minted by the same automation that consumes it — self-approval, which is not an approval (and is exactly the OD-24 question, not a design). Therefore: when `parallel.shard !== null`, plan projection — **before any context is created and before `ApprovalStore` is opened** — marks every protected step `refused` with `APPROVAL_REQUIRED` (**exit 14**, existing code, reason `approval_not_bindable_in_shard`), dispatches none of them (zero clicks, zero non-GET requests from them), runs all non-protected permitted actions and all read/assert steps normally, and the shard's final exit is 14. Additionally `PILOT_APPROVAL_RUN_TOKEN` **present** in shard mode is itself a refusal (`APPROVAL_RUN_TOKEN_INVALID`, exit 14, reason `run_token_in_shard_mode`) — this is what structurally prevents the shared-CI-secret design from being bolted on later. No claim marker is ever created in shard mode, so D-3's per-process claim invariant is untouched, and there is still no `--pilot-worker`, no `PILOT_WORKER` and no receipt surface (rev 4's D-3 paragraph otherwise unchanged).
6. **A missing, denied or lost state fails that shard closed; the merge marks the coverage lost (AC-023).** A shard that cannot load or validate its role state exits `AUTH_STATE_MISSING` (11); a shard that loses authentication mid-run exits auth-loss (12). In both cases the shard still writes a **refusal bundle**: a schema-valid `manifest.json` with `exit.code` 11 or 12, `pilot: {authCoverage: "lost", reason}`, every page `disposition: "skipped"`, and zero fragments and zero journals — so the merge receives a complete shard set and can attribute the loss. `ShardMerge` then: refuses an incomplete set as today (`MISSING_SHARD`, exit 2 — also not a pass); computes `coverage.pagesTestedAuthenticated` counting **only** pages whose fragment carries `authContext.mode === "authenticated"` **and** whose owning shard reports `authCoverage: "intact"`; records `coverage.authCoverageLost: [shardIndex…]`; **never** promotes an anonymous-fallback page into authenticated coverage (an `authContext.mode === "anonymous"` page is reported `status: "unauthenticated"`, never `tested`); forces `report.result` away from `PASSED` whenever `authCoverageLost` is non-empty; and returns the highest-severity code by the fixed precedence **12 > 11 > 14 > 1 > 0** (existing codes only, OD-10 unchanged, no new code). `code 2` (rejected input) and `code 3` (non-durable) keep today's precedence above all of these. **A merge with no pilot manifest is byte-identical to `2572e73` in behaviour and output (AC-076).**

**Must criteria satisfied in shard mode, and how.** AC-021 (policy parity across modes): rule 4 — same manifest digest enforced at merge, same gate constructed per process; tested sequential/workers/shards. AC-022: rule 1 + rule 3 — state is loader-only and the bundle allowlist excludes every state-bearing type structurally, with `assertClean` at the single writer and re-verification at merge. AC-023: rule 6 — exit 11/12 per shard plus `authCoverageLost` in the merged report, result never `PASSED`. AC-051 (approval/CSRF/armed-gate parity): satisfied in Shape 1; in shard mode protected actions are refused before dispatch, so the criterion is met by refusal, not by weakening — no protected action is ever dispatched without an approval in any shape. AC-060 (auth-loss detection): rule 4 + rule 6, per shard, same detector. AC-067: rule 3. AC-073 (no secret in any artifact): rules 2+3, per-process registry over that process's own artifacts, nothing cross-process unscanned because nothing cross-process is unallowlisted. AC-076 (non-pilot baseline unchanged): rule 6 final sentence plus the additive-only schema change. AC-077 (deterministic refusal codes): rules 5+6 use only existing codes 11/12/14 with fixed precedence.

**Cost of the restriction (OWNER DECISION, OD-23 re-scoped; no risk accepted).** Protected (destructive/approval-bearing) actions cannot be executed in shard mode; such plans must run in Shape 1 (sequential or `--workers=N`), which supports them in full. Authenticated discovery, read/assert coverage and non-protected permitted actions scale across runners normally. Owner must confirm this restriction; the alternative is not "allow it" but "commission a shared, human-attested approval service", which is out of Phase 18 scope and would need its own security review.

**One registry per process; the bundle is an allowlist, not a union (L01 iv).** There is one boundary and one complete registry per process in both shapes; rev 3's cross-process `registryKey`/`secretIndex` union stays deleted, because a shard's registry only ever has to cover that shard's own artifacts (section 2b rules 2–3). Residual retained and documented: the merge cannot detect a secret that a tampered build embedded inside an allowlisted *string* field; the mitigations are the write-side `assertClean`, the closed schemas' length caps and `redactText`, and the 18F four-location artifact scan over the real 3-shard CI run.

--- REPLACE ADR-0038 in full ---
### ADR-0038 (new) — Pilot mode is single-process *per runner*; shard mode is supported with protected actions refused.
Context: rev 2/rev 3 specified a coordinator that spawns workers and passes a `runId`, a claim receipt and a per-run `registryKey` through a spawn environment. No such process exists: `--workers=N` is bounded async concurrency in one process (`ParallelSweep.js:61,88,181`, `Runner.js:121`; no `child_process`/`worker_threads` in `src/`), and shards are independent CI-started processes with no parent and a separate merge (`Args.js:77-78`, `ci.yml:365-454`). Rev 4 concluded from this that shard mode must be refused; that conclusion was wrong, because it confused "no shared secret" with "no shared *need* for a secret". Only one pilot control genuinely requires cross-process trust — the human approval and its single-claim run token. Decision: (a) in-process parallelism is one boundary registry, one token claim, one ledger-lock holder with in-process serialisation beneath it (unchanged); (b) **shard mode is supported**: each shard is a self-contained pilot process that loads its role state from local input through the strict loaders, owns its own registry, enforces the manifest-derived policy identically, writes only allowlisted `assertClean`-verified artifacts, and fails closed on missing/denied/lost state with exit 11/12; the merge verifies shard completeness and bundle conformance, attributes lost authenticated coverage, never counts anonymous fallback as authenticated, and aggregates exit codes; (c) **protected actions are refused in shard mode** (`APPROVAL_REQUIRED`, exit 14, `approval_not_bindable_in_shard`) and a run token presented to a shard is refused (`APPROVAL_RUN_TOKEN_INVALID`, exit 14), because an approval is a local human-reviewed ledger record protected by a local `O_EXCL` lock and a once-claimed token, and every cross-runner transport either converts a per-run secret into a long-lived shared one, gives N processes one claim, forks the unlockable chain, or degenerates into self-approval. Alternatives rejected: refusing shard mode entirely (rev 4 — makes AC-022/AC-023 and the 18A/18F propagation requirements unachievable, and buys no security that the six rules do not already provide); a CI-secret `registryKey`; a per-shard approvals root with shard identity in the digest (self-approval). Consequences: authenticated coverage scales across runners; protected actions require Shape 1 (OD-23); `Schemas` needs an additive change (below); the merge gains conformance and coverage-attribution duties and a fixed exit precedence; no new exit code (OD-10 intact). Status: accepted.

## 2c. Owner decisions folded into the design (D1..D11)

### 2c.1 D1 — `PLAN_INVALID` is scoped to pilot execute mode (BLOCKER-1 ACCEPTED, ADR-0039)

--- REPLACE the plan §6 "BLOCKER-1 (needs owner input, do not let me reinterpret it)" paragraph in full ---
**BLOCKER-1 is decided (D1/OWNER-01).** The `PLAN_INVALID` refusal of AC-033 applies **only** to pilot execute mode, i.e. a run in which `--pilot-manifest` is present **or** the selected `--role` is declared `authenticated: true` in a resolved manifest. In that mode a plan without `version: 2`, without `digest`, or without `digestAlgorithm` — including every plan written by `--save-plan` at `2572e73` — is refused `PLAN_INVALID` with reason `PLAN_NO_DIGEST`, **exit 2**, at `PlanFile.load`, before any browser launch, any context creation and any network activity. Outside pilot mode `--plan` replay of a v1 plan is **byte-identical to `2572e73`**: same acceptance, same `PlanError("PLAN_INVALID")` → exit 2 for malformed input, same `isKeyShapedValue` screen, no digest requirement, no new refusal. AC-033 and AC-076 both hold with no amendment to AC-076. The mode test is a single predicate, `PilotLifecycle.isPilotExecute(argv, manifest)`, computed once before `PlanFile.load` is called and passed in as an argument; it is never re-derived inside the loader and never read from the plan file itself, so a plan cannot elect its own mode.

--- APPEND to section 8 (plan digest) ---
**Two distinct documented features, never one.** The documentation must present these as separate features with separate names, separate commands and separate guarantees:
1. **Legacy plan replay** (`--plan=<v1 file>`, no pilot flags) — the PR #54 feature, unchanged, no digest, no manifest, no approval, no authenticated role, no pilot guarantee of any kind.
2. **Approved pilot-plan execution** (`--dry-run-plan=` to produce a v2 plan, review, then `--plan=<v2 file> --pilot-manifest=... --role=...`) — digest-bound, manifest-bound, drift-checked, approval-gated.
No document, help text, release note or README line may describe (1) as a pilot capability or imply that (2) accepts v1 input. `docs/pilot/operator-guide.md` carries the two workflows under two headings with an explicit "this is not the pilot path" note on (1). A prohibited-phrase check (AC-078) gains the phrases "replay a saved plan safely" and "plan replay is approved" applied to any sentence that does not name the pilot path.

### 2c.2 D2 — pilot runs carry no healing or locator evidence (OD-17-Q1 ACCEPTED, ADR-0040)

--- REPLACE rev 7 section 2b.5 items 1, 3 and 5 in full ---
1. **No sink, in any shape.** For the whole duration of a pilot run (every mode: sequential, `--workers`, shard, dry-run, merge) the following are **not written**: `reports/healing_logs.json`, `data/healing_pending.json`, `data/healing_decisions.json`, `data/locator_store.json`, `data/locator_memory.json`, any bundle journal event of a healing or locator type (rev 6 2b.1(a)(1)), any `HealingTrust` record, and any reduced locator-identity record of any shape, including the dropped `{strategyId, outcome, locatorKeyDigest}`. `HealingReport` and `HealingTrust` are switched off by construction at injection time, not by a per-call guard. **Reads are unaffected**: pre-existing locator memory may be consulted, because consultation is inbound and mutates nothing — subject to 2c.2(6).
3. **The only admitted observability is a closed-schema aggregate counter block** (m-19, now mandatory): a fixed, closed key set of non-negative integers, aggregated **per run only** — never per page, per role, per URL, per selector or per locator key; histogram keys drawn from a **closed enum** of strategy ids and outcome values owned by the code, never from free text, error messages, provider output or application strings; integer values only; emitted through `Logger.info` **only**. The block is **not** added to `timings.json` (whose closed schema of rev 6 2b.1(b) is unchanged), not to any bundle, not to any fragment, not to a report and not to a dashboard event. The closed key set is a frozen constant asserted by test; adding a key is a code change that must pass the four-location scan.
5. **Any future reduced record is a new feature.** Admitting any healing or locator record into a pilot artifact requires a new closed schema, a new bundle shape number, a new security review and an owner decision. It is not re-admitted by implementer discretion, by a configuration flag or by an environment variable; no such flag or key exists.
6. **Open-time writes are a defect, not a tolerated side effect** (m-17(b), mandatory). In pilot mode `LocatorMemory` and `HealingTrust` are either not opened at all or opened through an explicitly read-only path that performs no write of any kind, including a salt header, an envelope, a version stamp or a lazily created empty file. Whether `LocatorMemory.applyMerge`/open writes with zero events is **unverified** (SEC-07 unverified item) and must be settled by a test before 18A merges, because an open-time write would raise a **false** exit 17 on a legitimate pilot run.

--- REPLACE the rev 6/rev 7 DOC limitations wording about locator learning ---
A pilot run contributes **nothing** to locator memory, the locator store, healing-pending state or healing trust, in every run shape. Documentation must not claim, imply or illustrate that running a pilot improves future locator recovery, healing accuracy or self-healing confidence for the pilot application. Non-pilot healing behaviour and non-pilot recording are **unchanged from `2572e73`**; the switch is keyed on pilot mode only (AC-076).

### 2c.3 D3 — protected actions are refused in shard mode (OD-23 ACCEPTED, AMEND ADR-0038)

--- REPLACE rev 5 section 2b rule 5 first sentence, and APPEND the pre-flight rule ---
**Protected actions are refused in shard mode, and the refusal is pre-flight where it can be.** When `parallel.shard !== null`:
(a) If the bound plan **statically** contains any action whose recorded `classification` is `protected` or whose `requiresApproval` is true, the shard refuses **before any browser launch, any context and any `ApprovalStore` open**: `APPROVAL_REQUIRED`, **exit 14**, reason `approval_not_bindable_in_shard`. This is new in rev 8 and replaces the rev 5 behaviour of discovering the refusal mid-run for the static case; an operator learns at once instead of after a full shard.
(b) A protected control discovered at runtime (no plan row, or a classification raised at step 5) is refused at `gate.perform` with the same code and reason, without opening `ApprovalStore`; the shard still completes its read, assert and non-protected permitted steps and its final exit is 14.
(c) `PILOT_APPROVAL_RUN_TOKEN` or `PILOT_APPROVAL_RUN_TOKEN_FILE` present in shard mode is refused `APPROVAL_RUN_TOKEN_INVALID`, **exit 14**, reason `run_token_in_shard_mode`, **without opening or reading the file**; both keys are deleted from `process.env` in the same synchronous block. `--approve-action` or `--emit-token-to` with `--shard` is an argv refusal, **exit 1**.
(d) `run/approvals/` — including `run/approvals/runtokens/` — is never created in a shard; asserted absent on disk by test.
(e) **Protected actions execute only in Shape 1**: a sequential run, or a `--workers=N` run, on one host, with a local admitted filesystem and an interactive human approval. There is no distributed protected-action support in Phase 18. Documentation must not describe shard pilots as supporting protected actions, "approval in CI", "distributed approvals" or "protected actions at scale". The honest statement is: *authenticated read/assert coverage scales across runners; protected actions do not.*

--- APPEND a new subsection "2c.4a CI behaviour for protected actions" ---
1. **There is no approve step in any Phase 18 workflow.** `ci.yml` contains no `--approve-action`, no `--emit-token-to`, no `PILOT_APPROVAL_RUN_TOKEN`, no `PILOT_APPROVAL_RUN_TOKEN_FILE`, no approval artifact, no approval cache and no `run/approvals` path in any step, `env`, `with`, cache or artifact block.
2. **A protected action reached in CI is refused**, `APPROVAL_REQUIRED`, **exit 14**. The CI pilot job therefore runs dry-run plus non-protected execute. A job whose fixture plan deliberately contains a protected step **asserts exit 14** as its expected outcome; it is never a skip (AC-074) and never a green pass of a protected action.
3. **The approver label is audit metadata, never identity.** It is a non-secret run-scoped string. No document, report, dashboard view or log line may present it as authentication, authorisation or attestation of a person. It is bound into the audit entry for attribution and tamper-evidence only (OD-02 unchanged).
4. **What survives for interactive runs.** The interactive two-command workflow is unchanged: `--approve-action` prints the token once to stdout with `fs.writeSync(1, …)` for a human at a terminal, and `--emit-token-to=<path>` with `SafeFs.createExclusive` (`O_EXCL`, `0600`, uid-owned, `fsync` + directory `fsync`) remains available **for local, non-CI use** because it is the only transport that keeps the token out of captured stdout on a developer machine. `PILOT_APPROVAL_RUN_TOKEN` / `PILOT_APPROVAL_RUN_TOKEN_FILE` consumption is unchanged for the interactive execute. The module-level one-shot flag, the single-exempt-emission-channel rule, the boundary registration of the token and `rejectKeyCarrierFlags` (argv token → exit 1) are all unchanged.
5. **Static enforcement.** The m-7 static `ci.yml` check (rev 6 2b.4) is extended to fail the gate if **any** workflow job references an approve flag, either token key, an approvals path, or an artifact/cache whose `path` resolves under `run/approvals`. The check covers every job, not only pilot shard jobs.

### 2c.5 D5 — evidence-gated filesystem admission (OD-20 ACCEPTED, AMEND ADR-0030)

--- REPLACE the OD-20 statement wherever it appears (section 2a, ADR-0030, section 19a, plan §6) ---
**OD-20 is decided (D5/OWNER-04).** `SafeFs.assertLocalFilesystem(dir)` remains a **numeric** `fs.statfs().type` allowlist with no string comparison, no override flag and no environment escape, and admission is now **doubly gated**:
(a) **`tmpfs` and `zfs` may be admitted, but only when both conditions hold**: (i) SPIKE-FS has recorded the observed numeric type for that filesystem on the target platform into the committed evidence table, **and** (ii) the Phase 18 filesystem behaviour tests have verified, on that filesystem, that `open(..., "wx")` is atomic under contention, that `rename` is atomic over an existing target, and that `fsync` on a file and on its parent directory both succeed and are honoured by the semantics the ledger relies on. A filesystem is **never** admitted from its name, from an assumed magic constant, from documentation or from a kernel header — only from a recorded number plus passing behaviour tests.
(b) **`overlayfs`, `virtiofs` and `drvfs` are NOT admitted.** Unknown and unrecorded types **fail closed**: `PILOT_INTERNAL_ERROR`, **exit 18**, with an explicit, actionable message naming the observed numeric type, the path and the remedy ("move `run/` to an admitted local filesystem; see docs/pilot/operator-guide.md#filesystems"), never a silent skip, never a warning, never a degraded mode.
(c) **Consequence, which must be stated in the operator guide and in a compatibility matrix**: dev containers, WSL, and container-based or otherwise affected CI runners are **unsupported for pilot state (`run/auth`, `run/plans`) and for approval ledgers (`run/approvals`)**. Falcon does not run pilot mode there; it refuses with exit 18. The compatibility matrix is a table of {platform, filesystem, observed numeric type, admitted yes/no, behaviour-test result, date, host} committed as evidence.
(d) **Any later addition needs durability evidence plus a security review.** Expanding the table is not a maintenance edit. A capability probe remains explicitly **rejected as a substitute** for durability evidence (rev 4 N-5): it can show that the calls succeed, not that `fsync` is durable.
(e) **ext2/ext3 remain admitted as a consequence of sharing `0xEF53` with ext4** and **HFS+ remains refused until a value is observed**; both are unchanged and both stay on the residual list.

### 2c.7 D7 — arming lease parameters and binding scope (OD-22 ACCEPTED, ADR-0042)

--- REPLACE the rev 3/rev 4 arming-window statements and the OD-22 flag ---
1. **Window.** `windowMs` default **2000**, hard maximum **10000**, minimum **250**, integer milliseconds. A configured value outside `[250, 10000]`, non-integer, `0`, negative, `NaN` or non-numeric is a **configuration error**, refused before any browser launch: `MANIFEST_INVALID` naming the JSON path when it comes from the manifest, argv refusal **exit 1** when it comes from a flag. There is no clamping, no "nearest valid value" and no warning-and-continue.
2. **Binding.** An approval binds `{method, destination origin, destination canonical path, actionId, planDigest, manifestVersion, manifestDigest, manifestRevision, role, falconBuild}` as defined in section 9 (eight-field binding plus the method/origin/path triple of the lease). The lease additionally binds the page, the frame, the resource type and the body-size class per rev 4 N-2.
3. **The request must begin within the lease.** "Begin" is defined operationally as *the Falcon route handler observing the request*, because that is the only instant Falcon can measure; a request whose interception happens at or after expiry is aborted and counted. The definition is written into the code comment and the operator guide so the measured quantity is not mistaken for browser-internal request start.
4. **No automatic refresh, no extension, no renewal.** There is no code path that extends an open lease, and none that re-arms on a timeout.
5. **One lease authorises exactly one protected-action attempt.** Arming follows a durable `ApprovalStore.consume`; the lease is consumed by the first matching request; at most one lease exists per pilot context; while a lease is open any other `perform` on that context is refused `POLICY_ACTION_DENIED` / `arming_window_open`. A failed attempt does not restore the lease or the approval: the approval is spent.
6. **Expiry fails closed.** On expiry the lease is destroyed, `armExpired: true` is recorded, every later non-GET is aborted as if nothing were armed, and no retry is attempted. A document load of a different URL expires the lease immediately.
7. **Disclosed limitation.** For a UI-dispatched action the **request body is not cryptographically bound** by the approval: the page generates it after the click. An already-hostile page can alter field values inside the approved `{method, origin, path}` while the lease is open; it cannot change the target, method, page, frame, resource type or size class. This is disclosed in `docs/pilot/limitations.md`, in the operator guide next to the window setting, and in the approval review output itself, and it is the reason the window is small.

### 2c.11 D11 — unknown state-changing actions default to protected (DESIGN CHANGE, ADR-0043)

--- DELETE and REPLACE rev 2 section 6 "Fail-closed rules" to the extent it permits a permit-by-default, and REPLACE threat-model section 6 item 4 ---
Delete every statement, in the architecture, the patches, the threat model and the owner packet, that an action may be classified `permit` because its vocabulary is unfamiliar — including the threat-model section 6 item 4 sentence "Novel vocabulary not listed in the manifest may be classified permit". The unfamiliarity of a term is **not** evidence that an action is safe.

**New normative classification policy (section 6, replacing the default).** `ActionClassifier.classify` returns one of `{permitted, protected, denied, ambiguous}` and `PolicyEngine` applies, in this order:
1. **Explicit denies stay denied.** A manifest `actions.denied` match, or a denied route for the request's own method, yields `POLICY_ACTION_DENIED` with no approval consulted and no gate armed (OD-18, AC-048 unchanged). Nothing in this section can raise a denied action.
2. **Detected destructive signals yield `denied` or `protected`, never `permitted`.** Any destructive signal in any input wins over every non-destructive signal (AC-043 unchanged, now explicitly non-overridable).
3. **Write-capable and state-changing actions default to `protected`.** A control is **state-changing-capable** when any of these holds: it is a `submit` control, or any control inside a `form`; its owning form's method is not `GET`; it is an `input`/`button`/element whose activation is write-capable (`type=submit`, `type=image`, `type=reset`, a `button` with no `type`, an element with a `formaction`); its navigation destination is a non-GET target; or its declared or observed method is not `GET`/`HEAD`. Such a control that is **not explicitly permitted by manifest policy** is classified **`protected`** — not `permitted`. Previously such a control could fall through to a provisional permit; it no longer can.
4. **Ambiguous state-changing actions fail closed.** When the classifier cannot decide whether an action changes state — unknown role, unresolvable form, unparseable destination, conflicting signals, a normalisation that removes a destructive match, or two candidates sharing the derived identity — the outcome is `protected` if the action is state-changing-capable and `CONTROL_AMBIGUOUS` (zero clicks) otherwise. There is no path from ambiguity to permit.
5. **Provider output can never lower a classification** (AC-045 unchanged) and can never supply the explicit permit of rule 6. `applyProviderAdvice` may only raise `permitted → protected` or `protected → denied`.
6. **Every permitted action is traceable to manifest policy.** A `permitted` outcome requires a recorded, named justification: the manifest route/action policy entry (route, pattern, action key) that permits it, recorded on the plan row and in the policy reason chain. A `permitted` outcome with no such traceable source is a defect and is refused `PILOT_INTERNAL_ERROR` (exit 18) — the fail-closed rule of section 1 applies to the classifier's own output.
7. **A GET route is not assumed side-effect-free.** The HTTP method alone never establishes safety. A GET action executes only when (i) its route is allowed for GET by the manifest, (ii) it is permitted by rule 6, and (iii) it appears in a reviewed plan when a plan is bound. A destructive GET on an allowed route remains dependent on manifest authoring and stays on the residual list.
8. **Residual, documented.** A staging application that violates its own declared behaviour — a GET that deletes, a "View" that writes, a form whose handler ignores its method — can still cause a state change inside a permitted action. The network gate (section 7a rule 3) bounds this to requests that match no armed triple and aborts them, but it cannot bound a server-side effect of an allowed GET. This is the honest limit of the control and must be stated in `docs/pilot/limitations.md`.

**PR ownership for D11:** **18C** owns `ActionClassifier.js`, `Vocabulary.js`, `PolicyEngine.js` steps 5, 6 and 9, the state-changing-capable predicate and the traceability record. **18B** owns the gate-side half: the plan row carrying `classification` plus the permit justification, and the refusal of a plan row whose `permitted` classification has no justification.

## 2d. Items this patch raises and does not accept (for owner or SEC-08)

- **OD-24-Q1 (needs owner or Security answer before 18D/18F merge).** D4 forbids a CI approve step, but **AC-051 (Must)** requires proof that an *approved* protected submit succeeds with an in-run token, and **AC-074 (Must)** forbids skipped tests in CI. These cannot all hold if "no approval in CI" is read to include the hermetic regression test. The design proceeds on the **narrow reading**: the prohibition covers (i) the `falcon.js --approve-action` CLI in any workflow, (ii) any CI run performing a protected action against a staging or non-fixture target, and (iii) any CI transport of a run token; it does **not** cover a hermetic regression test that constructs the approval through the `ApprovalStore` module API inside the test process, against the loopback fixture, with `approver: "test-fixture"` and an approval bound to the fixture origin. Under the narrow reading AC-051 and AC-074 both hold and no Must is weakened. Under the strict reading, AC-051's approved half becomes local-only and **AC-074 must be amended by the owner** to exempt it — a Must change I will not make. Owner must pick.
- **OD-20-Q1 (needs owner answer before tmpfs is added to the table).** `tmpfs` is volatile memory: `fsync` returns success and the bytes do not survive a reboot. Behaviour tests can prove atomicity and ordering; they cannot prove durability, because there is none. Recommendation: admit `tmpfs` for `authRoot` and `plansRoot` (run-scoped data) and **refuse it for `approvalsRoot`** unless the owner explicitly accepts that approval and audit history is lost on reboot. Loss fails closed (a missing ledger yields `APPROVAL_REQUIRED`), so the exposure is loss of tamper-evident history, not a bypass. No numeric filesystem id is asserted here: only values observed by SPIKE-FS and committed to the evidence table are admissible, and SPIKE-FS records whether the platform's tmpfs id is shared with ramfs (rev 9 m-21).
- **OD-22-Q1.** D7 gives no lower bound. I set **250 ms** so a value of 0 or 1 cannot silently disable protected actions while appearing configured. Confirm or change the number.
- **OD-22-Q2.** D7 says the request must begin within the lease but does not say what happens to **redirect hops** of an already-matched request that continue past expiry. Decision taken: the lease is consumed by the first matching request; later hops of that same request are validated against origin/route policy and the redirect cap but do **not** require a live lease, otherwise an approved POST that redirects at t > window would be aborted half-performed. Confirm.
- **m-17-Q1.** Whether `LocatorMemory` writes on open with zero events is still **unverified**. 2c.2(6) makes it moot if implemented, but the verification test is a merge condition for 18A, not an assumption.
- **OD-23-Q1.** Exit 14 outranking exit 1 (accepted residual) means a shard pilot that merely *contains* a protected action is indistinguishable at the exit code from a genuine approval failure. The receipt's `shardCodes` and `reason` distinguish them; if the owner wants a distinction at the exit code, that needs a new code and reopens OD-10.

## D. ADR additions and amendments (ADR-0038 is the shard decision; new numbers start at 0039)

- **ADR-0039 (new) — `PLAN_INVALID` for a digest-less plan applies to pilot execute mode only.** Context: AC-033 read literally breaks PR #54 v1 replay and contradicts AC-076. Decision: the refusal is gated on a single pre-computed pilot-execute predicate passed into `PlanFile.load`; non-pilot v1 replay is byte-identical to `2572e73`; legacy plan replay and approved pilot-plan execution are documented as two separate features. Consequences: two documented paths to keep distinct; a v1 plan is upgraded only by re-deriving a v2 plan from an observed page, never by rewriting the file. Status: accepted (owner D1/OWNER-01).
- **ADR-0040 (new) — pilot runs produce no healing or locator evidence; only closed-schema aggregate counters.** Context: OD-17 excludes healing evidence, and `HealingReport`/`HealingTrust` write uploaded artifacts and protected stores. Decision: both sinks off by construction in pilot mode; locator state read-only or unopened; observability limited to a closed key set of per-run integers with closed-enum histogram keys through `Logger` only; no bundle, report, dashboard or `timings.json` surface; any future record needs a new schema and a security review. Consequences: authenticated pages never improve locator memory or healing statistics, and no document may claim otherwise. Status: accepted (owner D2/OWNER-02).
- **ADR-0041 (new) — CI may not approve; protected actions in CI are refused.** Context: a job that mints and consumes its own approval is not a human approval. Decision: no approve step, approve flag, token key, token file or approvals path in any workflow; a protected action in CI is refused exit 14; the interactive stdout and `--emit-token-to` transports survive for local use; the approver label is audit metadata. - **ADR-0042 (new) — arming lease parameters and binding scope.** Context: an SPA fires its request after `click()` resolves, so a bounded arming window is required, and the body cannot be bound for a UI-dispatched action.

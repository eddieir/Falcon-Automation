## 6a. M-16 — the ledger brand has no constructor (REPLACES rev 11 5a.2 items 1–3, 5a.3 steps 2–3 preamble, 5a.5 case 10; AMENDS ADR-0041, ADR-0044)

### 6a.1 Decision

The ledger/fixture discriminator is **not a class brand**. `src/core/pilot/approval/ApprovalStore.js` holds, at module scope:

```
"use strict";
const WeakSetAdd = WeakSet.prototype.add;      // captured before any test code runs
const WeakSetHas = WeakSet.prototype.has;
const LEDGER_REGISTRY = new WeakSet();          // never exported, never reachable
const register = (approval) => { WeakSetAdd.call(LEDGER_REGISTRY, approval); return approval; };
const isLedgerApproval = Object.freeze((v) =>
    v !== null && (typeof v === "object" || typeof v === "function") && WeakSetHas.call(LEDGER_REGISTRY, v));
```

1. **No class, anywhere in the approval module graph, is used as or near the discriminator.** There is no `LedgerApproval` class, no `prototype`, no `.constructor`, no `instanceof`, no `Reflect.construct` target and no subclassable value. The M-16 attack class is **absent**, not guarded (P3).
2. **Approval objects are null-prototype and deep-frozen.** `#sealVerified()` builds the approval with `Object.create(null)`, copies only the verified fields, deep-freezes the object and every nested object and array, asserts `Object.isFrozen` and `Object.getPrototypeOf(x) === null` on each, and only then calls `register`. A failure of either assertion is `PILOT_INTERNAL_ERROR` exit 18, reason `approval_not_sealed`. Every nested object is itself `Object.create(null)`, so `Object.prototype`, `Array.prototype` and `Function.prototype` pollution is not even *inherited*-visible on an approval (P5).
3. **`register` is a captured private function** called from exactly one private call site, `ApprovalStore`'s `#sealVerified()`, invoked only after the full existing verification sequence succeeds (hash-chain verification over the segmented audit log and anchors, eight-field binding equality, `falconBuild` identity, run-token claim, the local lock, and the exclusive `O_EXCL` consumption marker with file and parent `fsync`). **Registration and verification are the same code path and may not be split into separate exported functions.**
4. **What is exported.** `module.exports = Object.freeze({ ApprovalStore, isLedgerApproval })`. The predicate only. There is **no** exported `brand`, `register`, `add`, `seal`, `mint`, `import`, `WeakSet`, symbol, or class whose construction registers. `add`/`has` are captured at module load so a later `WeakSet.prototype` monkeypatch cannot register anything (P4) — strictly stronger than rev 11, where the installer was a reachable constructor body.
5. **Why not the class-with-key design.** Design A (module-private `SEAL_KEY`, `Object.setPrototypeOf(this, null)`, `delete LedgerApproval.prototype.constructor`) also defeats every probe (P2). It is rejected because it depends on **three** negative invariants holding simultaneously and forever (the key never escapes, the prototype link is always severed before return, `prototype.constructor` stays deleted), any one of which a future edit can silently break while all tests still pass; and because the installer — a constructor body — continues to exist. Design B depends on **one** invariant (`register` is never exported), which the 18F static and runtime mint-scan checks of 6h directly falsify. The security property is at least equal and the surface is smaller. *This is an architect choice of mechanism; SEC-11 offered both and asked for probe evidence — it is recorded in the unsound-or-underspecified list as item 15.*
6. **Residual that is unchanged.** A registered approval is a capability-by-identity held in-process. Anything that already holds a genuine approval can pass it on; it cannot copy, forge, serialise, clone, proxy or re-bind it (P3), and its binding is immutable, so the eight-field binding equality still refuses it for any other plan, manifest, role, origin, action or build. This is the pre-existing "code in the approved process holds the approval" residual, not a new one.

### 6a.2 `gate.perform` — amended steps

Rev 11 5a.3 stands with these replacements:
- Step 2 becomes `isLedgerApproval(approval) === true` where the predicate is the registry predicate above. **Nothing else grants ledger class** — not a declared value, not a constructor name, not `instanceof`, not a prototype, not a caller-supplied predicate.
- Step 3(a) becomes: `Object.getPrototypeOf(approval) === null`, `Object.isFrozen(approval)`, and the same for `approval.binding` and every nested object and array; otherwise `APPROVAL_REQUIRED` exit 14, reason `fixture_approval_mutable`.
- Step 3(b)–(e) unchanged **except** as amended by 6c. Step 3(f) is **replaced** by 6d.

### 6a.3 Test-form correction (flag 3)

Frozen writes are a **silent no-op** in sloppy CommonJS (P16). Every frozen-write case in `neg-ledger-brand` and `neg-fixture-approval-scope` asserts **the value is unchanged and the brand/classification is unchanged**, and must not assert that a `TypeError` is thrown. The approval, gate, writer and fixture modules all begin with `"use strict"`, and an 18F static check asserts that.

## 6b. m-34 — the in-process writer REFUSES; it never prompts (REPLACES rev 11 5a.2 item 4 and 5a.5 case 9)

### 6b.1 SEC-11's remediation is unsound as written

"`write()` also refuses unless `require.main` is the `falcon.js` module (real path captured)" is forgeable in-process: `process.mainModule = {filename: "<…>/falcon.js"}` makes every subsequently loaded module see that object as `require.main` (P13), and the real main module's `filename` is writable. A path compare — captured or not — is not a control.

### 6b.2 Normative separation

1. **The interactive writer is an entry-only process.** The writer moves to `src/core/pilot/approval/approve-action.js`. Its first statement after `"use strict"` is `const IS_ENTRY = require.main === module;`, evaluated **once**, at its own first load. If `IS_ENTRY` is false the module exports **only** `{ isEntry: false, refusalReason: "approve_writer_not_entry" }` — no writer function of any name exists on the exports object — and any in-process call site therefore cannot write, **deterministically, under a pipe and at a real terminal alike** (P14). Object identity cannot be forged: the module object does not exist before its own first load, and the body runs exactly once, so a later `process.mainModule` assignment to the cached module object is inert.
2. **`falcon.js --approve-action` is still the single human interface** (OWNER-09, AC-084 wording unchanged). Its branch first asserts `require.main === module` for `falcon.js` itself; if false it refuses exit 1, reason `falcon_not_entry`, writing nothing. Then it re-executes the writer: `spawnSync(process.execPath, [APPROVE_ACTION_PATH, ...literalArgs], { stdio: "inherit", shell: false, env: <allowlist> })` where `APPROVE_ACTION_PATH` is `require.resolve("./src/core/pilot/approval/approve-action.js")` (literal) and the child's exit code is propagated unchanged. No shell, no argv-derived module path, no key-carrier flag (the existing `rejectKeyCarrierFlags` check at `falcon.js:477` runs first, unchanged).
3. **The child's gate, in this order.** (i) `IS_ENTRY` true; (ii) `CI` and `GITHUB_ACTIONS` unset → else exit 1 `approve_flag_in_ci`; (iii) `require("node:tty").isatty(0) && isatty(1)` — the syscall, never `process.stdin.isTTY`, which is assignable (P15) → else exit 1 `approve_flag_non_interactive`; (iv) the **bound prompt** is rendered: role, origin, HTTP method, canonical path, manifest digest, plan digest, `falconBuild` id and the approvals root real path, each on its own line, **before** any challenge is generated; (v) a freshly generated random challenge phrase is printed and read back from fd 0, with **no parameter, option, env key, config key or file** by which it can be supplied → else exit 1 `approve_challenge_failed`.
4. **Every prompt is audited, including refusals.** The writer appends an audit entry for each prompt rendered — the eight binding fields, the outcome (`approved`, `challenge_failed`, `aborted`) and the run id — as part of the hash chain, before the ledger entry is written. A prompt solicited by anything other than the operator is therefore visible after the fact. This is new tamper-evidence that rev 11 did not have.
5. **`ApprovalStore` still exposes no writer.** `consume`, `verify` and read accessors only (rev 11 5a.2 item 4, unchanged).
6. **Residual, stated not accepted.** Spawning the writer as a process entry reaches a human prompt; a human who reads the bound prompt and types the challenge is an approver by definition. `child_process` from a new or edited test file is the OWNER-10 accepted class, and this is owner residual 25, now bounded by items 3(iv) and 4.

### 6b.3 Tests (replace 5a.5 case 9)

`neg-ledger-brand` case 9 becomes three cases, each run **twice — under piped stdio and under a pty**, both expected identical:
- 9a: literal `require` of `approve-action.js` in-process; assert the exports object has no callable writer, `isEntry === false`, no ledger entry, `run/` digest set unchanged.
- 9b: `require` of `falcon.js` with `process.argv` pre-mutated to include `--approve-action`; assert exit 1 `falcon_not_entry` and no write.
- 9c: child `node falcon.js --approve-action` with `CI=true` → exit 1 `approve_flag_in_ci`; with piped stdio → exit 1 `approve_flag_non_interactive`; with a wrong challenge → exit 1 `approve_challenge_failed`; in all three, no ledger entry and the audit prompt entry present.
- Inversions: replace the identity check with a `require.main.filename` path compare and 9a/9b must fail; read `process.stdin.isTTY` instead of `tty.isatty` and 9c's piped case must fail.

## 6c. m-35 — server identity is reference identity, never shape (REPLACES rev 11 5a.3(b)(c)(d) rationale and 5a.4 item 4; AMENDS ADR-0044, threat-model item 20)

1. **Correction of the false claim.** The sentence "a duck-typed server cannot lie" is **withdrawn**. `Object.create(net.Server.prototype)` with an own `_handle.getsockname` satisfies `instanceof net.Server`, the captured `net.Server.prototype.address` and the captured prototype `listening` getter (P9). Captured intrinsics defeat only a **plain** duck-typed object. Every document carrying the claim is corrected (6k).
2. **What the captured intrinsics are retained for.** They remain mandatory as the *only* read path for address and liveness (they stop the own-`address()` and own-`listening` substitutions, which are the common case) and the module-load fail-closed on a missing descriptor (exit 18 `net_intrinsic_unavailable`) stands. They are **no longer claimed** to authenticate a server.
3. **m-35(c), normative.** A `PilotActionGate` constructed by `PilotRuntime` **refuses every unbranded approval**: `APPROVAL_REQUIRED` exit 14, reason `fixture_approval_in_production_runtime`, before any loopback evaluation. The fixture class is reachable only from a gate that test code constructed directly (rev 11 5a.4 item 3). Production therefore never relies on server authenticity at all, and **R-8 is acceptable as a stated residual** on that basis. Inversion: allow the fixture branch in a `PilotRuntime`-built gate and the case must fail.
4. **Fixture-side authenticity, by reference only.** `tests/pilot/fixtures/PilotFixtureServer.cjs` holds a module-private `WeakMap SERVER_RECORDS` with captured `WeakMap.prototype.set/get/has`. `start()` creates the server **inside this module** with `net.createServer()`, and on its own `listening` event records `{ listenEpoch, port, family, capabilityProof }`, incrementing `listenEpoch` on every `listening` event. Exports are **only** `start()` and the predicate `isFixtureServer(server)`; there is no `add`, `register` or record accessor. `FixtureApprovalAuthority`'s constructor requires, in addition to the production-side checks: `isFixtureServer(server) === true`; `SERVER_RECORDS.get(server).listenEpoch === <the epoch at this authority's construction>`; and the recorded `port`/`family` equal to the values read live through the captured intrinsics. **Nothing is compared by shape.** This refuses the prototype-built fake (P9), an independently created real loopback server including a forwarding one (P10), a closed server (P11, liveness false / address null) and a **closed-and-reopened** server, whose port and epoch both change (P12). A server from another run or another process can never be present: the registry is keyed by object identity in one process and one module instance.
5. **Address literals.** Unchanged: `127.0.0.1` / `::1` literal compare with an integer port 1..65535. `127.1` and `2130706433` normalise to `127.0.0.1` (same host, no widening); `localhost`, `0.0.0.0`, `::ffff:127.0.0.1` and `[::ffff:7f00:1]` fail the literal compare; `[0:0:0:0:0:0:0:1]` normalises to `[::1]`. All are named cases in 6h.
6. **Require-order assertion (closes SEC-11's UNVERIFIED intrinsics note).** An 18F check asserts that the gate module appears in the require graph of every pilot entry before any `tests/` module, and an 18D runtime case asserts the captured `ServerCtor`, `ServerAddress` and `ListeningGetter` are reference-identical to the live `node:net` values at first gate construction.

## 6d. m-36 — unfreezable values are excluded from approvals (REPLACES rev 11 5a.3(f) and the 5a.5 deep-freeze wording)

1. **Bindings and leases hold primitives only.** Strings, integers, booleans and `null`. **No `Date`, no `Buffer`, no typed array, no `Map`/`Set`, no function.** Timestamps are epoch-millisecond integers. Rationale: a frozen `Date` is still mutable through `setTime` (P7) and a `Buffer`/typed array **cannot be frozen at all** (P6, `TypeError: Cannot freeze array buffer views with elements`). `#sealVerified()` validates the field types against a closed schema and refuses otherwise with exit 18 `approval_not_sealed`, so the deep-freeze invariant of 6a.1(2) is total and no freeze exemption is needed on the approval object.
2. **`capabilityProof` moves off the approval.** It is held in a **gate-side module-private `WeakMap`** keyed by the approval object (captured `WeakMap.prototype.get/set/has`), written by the authority at resolve time and read by the gate at consume time, compared with `crypto.timingSafeEqual` against the value derived from the live server record. The approval object has **no `capabilityProof` slot** (P8: a frozen null-prototype key works; a copy is not a key). Consequences: the proof is not an own property, so it is not serialisable, cloneable, enumerable or pollutable; `Object.keys`, `JSON.stringify` and `structuredClone` cannot reach it; and a hand-built or cross-process object has no entry → exit 14 `fixture_approval_not_live`.
3. **AC-092's pollution key list drops `capabilityProof`** (no longer read off the object) and gains nothing: with null-prototype approvals, prototype pollution is not visible on an approval at all. The pollution cases stay in the suite as regression protection with that stronger expectation.

## 6e. m-37 — the missing/unverifiable partition is completed (AMENDS rev 11 5b item 3, ADR-0030, AC-085)

On the **resolved real path** of the approvals root:
1. **Missing** = `realpath(root)` gives `ENOENT` **and** `lstat(root)` gives `ENOENT`; **or** the root exists and is an **empty directory**. → `APPROVAL_REQUIRED` **exit 14**; trust is restored from nothing; a fresh initialisation writes the genesis entry.
2. **Dangling symlink at the root** (realpath `ENOENT`, `lstat` succeeds) → `PILOT_INTERNAL_ERROR` **exit 18**, reason `approvals_root_symlink`, under the existing no-symlink rule. It is **never** "missing".

5. **AC-085 matrix adds three rows**: empty directory → 14; dangling symlink → 18 `approvals_root_symlink`; non-empty-without-chain (lock only, marker only, unknown file only) → 18 `approval_history_unverifiable`. Inversion: treat "no ledger object" as missing and rows 3 must fail.

## 6g. Owner requirement 1 — the real interactive approval path, exercised as test automation (NEW; 18D test, 18F wiring)

**It automates the single production human interface. It is not a second mechanism.** No code is added to `src/` for it; the pty helper lives in `tests/` only.

### 6g.1 Location and wiring
- Test: `tests/regression/pilot/approval-interactive-path.test.js`, owned by 18D.
- Helper: `tests/pilot/bin/pty-approve.cjs` (pty allocation, prompt parsing, challenge typing), owned by 18D.
- Wiring: 18F adds a `pilot-manual` Playwright project / npm script `test:pilot-manual` with `testMatch` for this file only, **excluded from `.github/workflows/ci.yml` and from every CI-reachable script**.
- **It is local/manual only, and that is not an owner choice.** AC-084 (Must) fails on *any* approve flag reachable transitively from a workflow through npm/yarn/npx and node/bash invocations. A CI-run pty test would make `--approve-action` workflow-reachable and fail AC-084. Running it in CI therefore requires amending a Must criterion, which this patch may not do. SEC-11's recommendation (local/manual plus the static negative half in CI) is adopted as normative. CI runs only 6g.4.
- Consistency with **OWNER-09**: the test enables nothing. The temporary approval and audit roots are passed as **constructor-level config** to the spawned command's own argument list; no environment variable and no CLI flag enables, bypasses or supplies the interaction.

### 6g.2 Exact assertions (all must hold)
1. **Hermetic.** The target is a loopback fixture app from `tests/fixtures/pilot-app/**`. A network gate asserts **zero** non-loopback requests for the whole test, including DNS-resolvable hostnames.
2. **Isolated roots.** Fresh approvals root and audit root under `os.tmpdir()`, created by the test, outside the repository and outside `run/`.
3. **Environment stripped.** The child env is an explicit allowlist (`PATH`, `HOME` replaced by a temp dir, `TMPDIR`, `TERM`, `LANG`). Everything matching `*_KEY`, `*_TOKEN`, `*_SECRET`, `*_PASSWORD`, `CI`, `GITHUB_*`, `*_PROXY`/`*_proxy`, `NODE_OPTIONS` is absent. The test asserts the absence by key name only and **never prints a value**.
4. **Real path.** It spawns `node falcon.js --approve-action …` under a pty with `stdio` attached to the pty, so `tty.isatty(0) && isatty(1)` are genuinely true and the production code path of 6b.2(3) runs unmodified.
5. **Prompt binding proven.** It parses the rendered prompt and asserts **all eight** values equal the expected ones: plan digest, role, origin, HTTP method, canonical path, manifest digest, `falconBuild` id, approvals root real path. A missing or mismatched line fails the test.
6. **Approve once.** It types the challenge exactly once, through the pty, and asserts exit 0 and exactly one ledger entry whose chain verifies.
7. **Replay fails.** Re-presenting the same approval for a second attempt → `APPROVAL_REQUIRED` exit 14 (the exclusive consumption marker).
8. **Binding substitution fails.** Eight sub-cases, one per binding field, each mutating only that field of the attempt → exit 14.
9. **Cleanup.** The temporary roots are removed in teardown, and the real `run/` and `data/` digest sets are byte-identical before and after.
10. **No bypass.** A source scan asserts no CLI flag, env key, config key or file supplies the challenge or skips the prompt, and that `approve-action.js` has no export callable in-process (6b).

### 6g.3 Inversions (each must make the test fail)
Remove the `tty.isatty` gate; accept a challenge from argv or env; render the prompt **after** generating the challenge, or omit any one of the eight bound lines; drop the consumption marker (replay then succeeds); relax one binding field compare; drop the env allowlist.

### 6g.4 The negative half, which **does** run in CI
Piped stdio refuses; `CI=true` refuses; a wrong challenge refuses; the in-process require refuses (6b.3 9a/9b); `neg-ci-no-approve-step` and the AC-084 walker assert no workflow reaches an approve flag, the approve-action module or an approvals path. These are deterministic and need no pty.

### 6g.5 Documented limit (DOC, mandatory wording)
"This test proves that Falcon's production interactive approval path requires a real terminal, binds the prompt to the exact plan, role, origin, action and build, and refuses replay and binding substitution. It does **not** authorise CI to approve real customer actions, it creates no second approval mechanism, and it runs locally and manually only."

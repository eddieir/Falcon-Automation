
# Phase 18 architecture — revision 10 patch (ARCH-10)

Normative addendum to the [rev 9 patch](phase-18-rev9-patch.md). It implements the owner decisions recorded as OWNER-09 (OD-24-Q1), OWNER-10 (m-25 boundary acceptance) and OWNER-11 (OD-20-Q1, OD-22-Q1, OD-22-Q2), and closes SEC-09 m-25 at the design level. Base for compatibility claims is `2572e73`. No Must criterion, no OD-01..OD-19 and no recorded owner decision is weakened; three controls are strengthened (the fixture approval boundary becomes structural rather than environment-gated, filesystem admission becomes per root, and redirect continuation becomes method-observed rather than status-code-inferred). Nothing here authorises implementation, merge, tag or publication.

Status: DRAFT rev 10, pending SEC-10 on the rev 10 delta only. Six items are flagged as unsound, ambiguous or underspecified in section 4f rather than silently resolved; two of them (R-3, R-4) are decision points the owner or Security must confirm.

What changes, in one line each:
1. **3b.2 is replaced.** The CI environment-variable double gate (`CI`, `GITHUB_ACTIONS`, `FALCON_PILOT_TEST_RUNNER`) and `ApprovalStore.mintFixtureScoped` are **removed**. The fixture approval authority is a class that does not exist in the production require graph, injected into the gate by the test harness. Production construction cannot name it.
2. **A tests-only executable** is specified for subprocess exit-code coverage, with a fixed case enum instead of a URL and no filesystem dependency at all.
3. **The m-25 overclaim is corrected everywhere**, repository-write governance is named as the required control, and a recommended `CODEOWNERS` is given as a file, not as a claim about GitHub settings.
4. **Filesystem admission is per root**, tmpfs refused for the approval/audit root.
5. **Redirect continuation is method-observed**, with a 5 status-code SPIKE-R gate.

## 4a. OD-24-Q1 — the fixture approval boundary is structural (REPLACES rev 9 3b.1 and 3b.2 in full; AMENDS ADR-0041 and ADR-0044)

### 4a.1 The decision, as recorded (OWNER-09)

OD-24-Q1 is **ACCEPTED as a strictly fixture-scoped test approval**. CI may test the approved protected-action path only through a fixture-scoped, in-memory approval authority with: loopback-literal fixture origin only; a per-process, per-run, unexportable capability; no persisted approval ledger; no `run/approvals` path; no workflow approve step; no approval reusable by another process; no non-loopback target; **no production CLI option that directly enables test approval**; **no environment variable alone that enables it**; unavailable through normal `falcon.js` execution. AC-051 remains fully tested in CI. AC-074 is **unchanged** — no skipped and no expected-fail test. The AC-084 static workflow check is **defence in depth**; the runtime structural boundary is the primary control.

Rev 9 3b.1 (the two-reading cost analysis and the architect recommendation) is therefore **superseded and deleted**: the owner has chosen. Rev 9 3b.2 items 1–8 are **replaced in full** by 4a.2–4a.6 below. `ApprovalStore.mintFixtureScoped` is **withdrawn**: it was a production-reachable mint function on a production module, which OWNER-09 forbids.

### 4a.2 The injection seam (18D)

**Production approval resolution.** The only production path to an approval stays what rev 3..rev 8 specified: a durable ledger entry, written by an interactive human `--approve-action`, consumed once by `ApprovalStore.consume(binding)` under the local lock and the run token. The `ApprovalStore` constructor signature is **fixed and closed**:

`new ApprovalStore({ approvalsRoot, falconBuild, clock, lock })`

It accepts **no** approval-authority, no source list, no `mint*` callback, no `scope` and no test hook. It exposes **no** method that creates an approval from in-process state. There is nothing to pass, so nothing can be passed in production. (Rev 9's `mintFixtureScoped` is deleted from the API surface, from AC-090 and from ADR-0044.)

**The seam is one level above the store.** The component that *resolves* an approval for a protected action is an ordered, immutable list of approval sources held by `PilotApprovalResolver`:

```
// src/core/pilot/approval/PilotApprovalResolver.js (18D)
// Each source: { scope: string, resolve(binding) -> approval | null }
new PilotApprovalResolver({ sources })   // sources is frozen at construction
```

- **Production construction is a frozen literal in exactly one file.** `src/core/pilot/PilotRuntime.js` builds the resolver as `new PilotApprovalResolver({ sources: Object.freeze([ new LedgerApprovalSource(approvalStore) ]) })`. There is no flag, environment variable, config key, manifest field, plan field or argv path that appends, replaces or reorders a source. The `sources` option exists only because the test harness constructs the resolver directly.
- **`LedgerApprovalSource` is the only source implementation under `src/`.** A `require` graph assertion (4a.6 item 3) proves it is the only one.
- **A source whose `scope` is not `"ledger"` is refused inside `PilotRuntime`** (`PILOT_INTERNAL_ERROR`, exit 18, reason `non_ledger_source_in_production_runtime`). Production code therefore cannot construct the fixture authority *and* cannot smuggle an equivalent object through the production factory even if one were written under `src/`.

**The fixture authority is not production code.** `FixtureApprovalAuthority` lives at `tests/pilot/approval/FixtureApprovalAuthority.cjs`. No file under `src/`, `scripts/`, `falcon.js`, `package.json`, `.github/` or any workflow references it. Because production construction cannot name it, production can never obtain it — that is the primary control, and it holds without any environment variable.

### 4a.3 `FixtureApprovalAuthority` — what it may do, enforced by its own construction (18D, test-owned)

```
new FixtureApprovalAuthority({ server, capability })   // scope === "fixture"
authority.resolve(binding) -> approval | null
```

1. **It cannot exist without a server it did not receive from a caller as a URL.** The constructor accepts only a live `net.Server` **object** created by `tests/pilot/fixtures/PilotFixtureServer.cjs#start()` in **this** process, plus the 32-byte capability that `start()` returned to its single caller. There is no string origin, host, port or URL parameter anywhere on the constructor or on `resolve`. The approved origin is **derived** from `server.address()`, never supplied.
2. **Loopback literal, derived and re-derived.** The derived address must satisfy `family === "IPv4" && address === "127.0.0.1"` or `family === "IPv6" && address === "::1"`, and `server.listening === true`, checked at construction **and again on every `resolve`**. `localhost`, any hostname and any non-loopback literal are impossible to express, not merely refused. `PilotFixtureServer.start()` binds `{ host: "127.0.0.1", port: 0 }` as literals; it takes no host or port parameter.
3. **Per-process, per-run, unexportable capability.** `start()` generates the capability with `crypto.randomBytes(32)`, keeps it in a module-scoped `WeakMap` keyed by the server object, returns it to its caller once, and exposes no getter. `resolve` compares with `crypto.timingSafeEqual`. The capability is never serialised, logged, written, placed in an environment variable or printed; the section 9 secret-boundary registration applies to it. It is not derivable in a second process, so no approval minted here is usable by another process.
4. **No handler, upstream or proxy surface (SEC-09 m-25(c)).** `start()` accepts no request handler, upstream, proxy, target or rewrite option and serves only the fixed, in-repo fixture app. A pilot context that resolves a `scope: "fixture"` approval additionally refuses any browser launch `proxy` option and any `--proxy-server` argument (`PILOT_INTERNAL_ERROR`, exit 18, reason `fixture_approval_with_proxy`), because a proxy that does not bypass loopback forwards a loopback-approved request onward.
5. **No persistence surface, structurally.** `FixtureApprovalAuthority.cjs` and `PilotFixtureServer.cjs` **do not require `node:fs`, `fs/promises`, `SafeFs`, `ApprovalStore`, `AuditLog` or `RunToken`**, directly or transitively. They hold the approval in a local variable and return it. **Consequence:** no `run/approvals` path, no ledger file, no audit-chain entry, no run-token file and no receipt can be created for a fixture approval, because the code that would do it is not in the module's require graph. This is asserted statically (4a.6 item 3) and behaviourally (4a.6 item 1), and it is the property that makes "no persisted approval ledger" checkable without trusting a conditional.
6. **One attempt, no reuse.** `resolve` returns an approval at most once per `(authority, binding)`; the second call returns `null`. The approval object is not cloneable into a usable state: it carries a non-enumerable reference to the live server object, so `JSON.parse(JSON.stringify(approval))` yields an object the gate refuses (`APPROVAL_REQUIRED`, exit 14, reason `fixture_approval_not_live`).
7. **Binding equality is unchanged and additional.** The eight-field binding of section 9 plus the lease `{method, origin, path}` triple apply exactly as for a ledger approval. The manifest-confinement rule of rev 9 3b.2(4) is retained verbatim: `binding.manifestDigest` must be the digest of a resolved manifest **every** one of whose route origins is that same derived loopback origin.
8. **Consumption re-check at `gate.perform` (retained from rev 9 3b.2(7)).** A `scope: "fixture"` approval is consumable only when the live destination origin equals the derived loopback literal and port, the live manifest digest matches, and `server.listening` is still true. Anything else → `APPROVAL_REQUIRED`, **exit 14**, reason `fixture_approval_non_loopback`. This check lives in **production** code (`PilotActionGate`), so it holds even if the test-side authority is modified.

**Deleted, with the reason stated:** rev 9 3b.2(1)'s `FixtureServer.js` module registry under `src/` (the fixture server is test code now, so no registry under `src/` is needed), rev 9 3b.2(5) in full (environment-variable double gate — forbidden by OWNER-09 as an enabling or gating control), and `mintFixtureScoped` (production-reachable mint function — forbidden by OWNER-09).

### 4a.4 How AC-051 is tested in CI (18D/18F; AC-074 unchanged)

**(a) In-process, primary.** `tests/regression/PilotApprovedProtectedAction.check.cjs` starts the pilot fixture server, obtains the capability, constructs `FixtureApprovalAuthority`, and constructs `PilotApprovalResolver` **directly** with `[ledgerSource, fixtureAuthority]`. It then drives the real `PilotActionGate` through an approved protected submit on the CSRF fixture and asserts: the POST succeeds; the in-run token value appears in **zero** artifact bytes (the four-location scan); `run/approvals` does not exist; no file under `run/` was created or modified (digest set before and after). The unapproved half (zero POSTs) is unchanged. This runs in the normal `npm run test:regression` gate on Node 24 in CI, not skipped, not expected-fail.

**(b) Subprocess, for the exit codes only.** Falcon's exit codes are CI-sensitive and must be tested directly, so the approved-success exit 0 and the `fixture_approval_non_loopback` exit 14 are also proven through a **dedicated tests-only executable**:

`tests/pilot/bin/approved-fixture-case.cjs`

- It accepts **exactly one** argument, `--case=<id>`, where `<id>` is a key of a frozen literal map of in-repo cases (`csrf-approved-submit`, `csrf-unapproved-submit`, `fixture-approval-vs-non-loopback`). **It accepts no URL, origin, host, port, path, manifest path or plan path.** An unknown case, a missing case, a repeated flag or any additional argument exits 2 with `FIXTURE_CASE_UNKNOWN` and starts nothing.
- It **creates the fixture server itself** with `PilotFixtureServer.start()` and holds the capability it returns. It never adopts, registers, probes or connects to a server it did not create (see R-3 in 4f: the owner's "creates the fixture server itself **or** verifies its per-run capability" is implemented as **and**).
- It builds the manifest and the plan for the case from in-repo fixture files resolved by `path.join(__dirname, …)` from the case map, so the target cannot be redirected by an argument or an environment variable.
- It requires `FixtureApprovalAuthority` and therefore inherits every property of 4a.3, including the absence of any filesystem module in its require graph for the approval half.
- **Isolation.** It lives under `tests/`, is named by **no** `package.json` script, is required by no file under `src/`, `scripts/` or `falcon.js`, and is not a workflow step. It is invoked only by `execFile(process.execPath, [path.join(__dirname, "..", "pilot", "bin", "approved-fixture-case.cjs"), "--case=…"])` from the regression check in (a).
- **Reachability through `falcon.js` is structurally impossible**, not flag-gated: `falcon.js` never requires it, and no argv value selects a module to load. (Observed today: `falcon.js:474-540` parses only known literal flags and ignores unknown ones, so there is no "unknown flag" surface that could ever reach it either.)
- **Defence in depth only, labelled as such:** the executable also asserts `path.resolve(process.argv[1])` is under `<repoRoot>/tests/` and refuses otherwise. `process.argv` and `process.env` are writable in-process, so this is an accident guard, never a boundary (SEC-09 m-25).

**(c) The run-token path in CI.** Unchanged: no workflow step, flag, environment key or artifact carries a run token (AC-084). The fixture approval does not use a run token file; the in-run token is created and consumed inside the one process.

### 4a.5 CLI accident guards (retain, relabel; do not use as the boundary)

Rev 9 3b.2(8) is **retained but reclassified**: `--approve-action` and `--emit-token-to` refuse with **exit 1**, reason `approve_flag_in_ci`, when `CI=true` or `GITHUB_ACTIONS=true`, **and** `--approve-action` additionally requires `process.stdin.isTTY && process.stdout.isTTY` (SEC-09 m-25(d)), refusing exit 1 reason `approve_flag_non_interactive`. Both are **accident guards against a mis-authored workflow or a captured stdout**. Neither is part of the fixture boundary, neither enables anything, and both are explicitly documented as forgeable by anyone who can set the environment of a child process. Keeping them weakens nothing and removes no control; `FALCON_PILOT_TEST_RUNNER` is gone and must not reappear in any form.

### 4a.6 Tests (QA; every `neg-*` needs its inversion demonstrated failing)

1. **`neg-fixture-approval-scope` (18D, U/R/S) — replaces the rev 9 case list.** Required cases: construct the authority with a server that is not listening → refused; with a server bound to a non-loopback address (bind `0.0.0.0` in the test, then assert the derived address check refuses) → refused; with a wrong or zeroed capability → refused (timing-safe compare); with a manifest containing one non-loopback route origin → refused; consumption against a staging-like non-loopback origin → `APPROVAL_REQUIRED` exit 14 reason `fixture_approval_non_loopback`; a pilot context with a launch `proxy` or `--proxy-server` while a fixture approval is resolved → exit 18; a serialised/replayed approval → exit 14 reason `fixture_approval_not_live`; a second `resolve` for the same binding → `null`; `run/approvals` absent and the `run/` digest set unchanged after the whole suite. **Inversions:** delete the derived-address check, the liveness re-check, the capability compare, or the production-side consumption re-check, and the corresponding case must fail.
2. **`neg-fixture-no-arbitrary-target` (18D, U/R) — the OWNER-10 blocker test, run with the repository source unmodified.** The test may only use the public surface: it enumerates every own and inherited property of the authority, the server wrapper and the resolved approval, and attempts, by argument, property assignment and prototype mutation, to (i) point the approval at any non-loopback origin, (ii) point it at a second loopback port it did not create, (iii) obtain the capability, (iv) cause any write under `run/`, `data/` or the repository. Every attempt must fail, and the post-condition is a byte-identical filesystem. **Any demonstrated path from the fixture authority to an arbitrary target or to persisted approval state is a BLOCKER (OWNER-10) and stops 18D.**
3. **`neg-fixture-require-graph` (18D/18F, S) — static, and the cheapest guard.** Walking literal `require()` from `tests/pilot/approval/FixtureApprovalAuthority.cjs` and `tests/pilot/fixtures/PilotFixtureServer.cjs`, the transitive set contains **no** `node:fs`, `fs`, `fs/promises`, `SafeFs`, `ApprovalStore`, `AuditLog`, `RunToken`, `child_process` or `net.connect` usage beyond `net.createServer`. Walking literal `require()` from `falcon.js` and from every `src/` entry, the transitive set contains **no** path under `tests/`. `PilotRuntime.js` contains exactly one `PilotApprovalResolver` construction and exactly one source. **Inversions:** add an `fs` require to the authority, or require the authority from `src/`, and the check must fail.
4. **`neg-ci-no-approve-step` (18F, S)** keeps every rev 9 3b.3 and SEC-09 m-24 case, minus the `FALCON_PILOT_TEST_RUNNER` token (the key no longer exists), plus: a workflow step that invokes `tests/pilot/bin/approved-fixture-case.cjs` directly, outside the regression gate, must fail the gate; `--case=` with anything other than a frozen map key must fail the gate.
5. **AC-074 evidence** is the regression gate run itself: zero skips, zero expected-fails, and the approved half present.

### 4a.7 AC-084 static check — retained as defence in depth (18F)

Rev 9 3b.3 items 1–6 and SEC-09 m-24 (a)–(f) are **retained in full and unchanged**, with two edits: the `FALCON_PILOT_TEST_RUNNER` term is removed from the fail list (the key is withdrawn), and the gate additionally fails on any `require` of a path under `tests/` from a file under `src/` or `scripts/`, and on any workflow invocation of a tests-only executable outside the test gate. The check's status is stated in the ADR and in the threat model as **defence in depth; the structural boundary of 4a.2–4a.3 is the primary control**. A static-check gap is therefore a defect, not a bypass.

## 4b. m-25 — the repository-trust limitation, stated honestly (OWNER-10)

### 4b.1 Normative wording (REPLACE the overclaim in rev 9 3b.1, ADR-0041, ADR-0044 and threat-model §6 item 20)

**Delete the phrase "The exposure is therefore a self-contained in-repo test, not a path to a staging mutation" and every paraphrase of it.** Replacement text, to be used verbatim in all four places:

> The fixture approval boundary confines **production code paths and mis-authored workflow steps**. It does **not** defend against an author who can modify repository code, tests or workflows: such an author can add a test that spawns `falcon.js` with a computed flag string and a cleared `CI` variable, which produces a persisted, non-loopback CLI approval, and can edit the fixture authority itself. The controls for that actor are **code review, protected branches and repository write governance**, which are organisational controls outside Falcon's code. Falcon makes no claim about which GitHub repository settings are enforced. Within the unmodified repository the fixture authority cannot target a non-loopback origin and cannot persist approval state, and that property is tested (`neg-fixture-no-arbitrary-target`); outside it, the boundary is a code-review question.

This is the limitation the owner accepted (OWNER-10). It **does not** authorise a CI workflow to approve its own real pilot action, and AC-084 continues to forbid any approve step.

## 4c. OD-20-Q1 — per-root filesystem admission (OWNER-11; AMENDS rev 9 3c m-21(c) and ADR-0030)

**OD-20-Q1 is ACCEPTED.** Normative rules, replacing rev 9 3c m-21(c) and the OD-20-Q1 open item:

1. **Per root.** `SafeFs.assertLocalFilesystem(dir, rootKind)` with `rootKind ∈ {auth, plans, approvals}` and a **per-root** admitted-id set. Admission is evaluated separately for every root, on the resolved real path of that root, at pilot start, before any write.
2. **tmpfs.** May be admitted for the **ephemeral authentication-state root (`run/auth`)** and the **plan working root (`run/plans`)** after the required behavioural checks of rev 8 2c.5(a)(ii) as corrected by rev 9 m-21(b) (`O_EXCL` atomic under contention; `rename` atomic over an existing target; `fsync` on file and parent directory each return success with a consistent fresh-process read-back; **no durability claim**). **tmpfs is REFUSED for the approval and audit-history root (`run/approvals`)**: `PILOT_INTERNAL_ERROR`, **exit 18**, reason `approvals_root_not_durable`, with the observed id, the path and the remedy.
3. **ZFS** remains conditional on SPIKE-FS evidence: an observed, committed numeric id **and** passing behaviour checks, per root. No id from a kernel header, documentation or reviewer knowledge (rev 9 m-21(a) stands).
4. **Unknown types fail closed** on every root: exit 18, actionable message naming the observed id and the path, never a skip, never a warning, never a degraded mode.
5. **Missing approval history yields `APPROVAL_REQUIRED`** (exit 14) and **never restores trust from another source**: not from a receipt, a bundle, a report, a cache, an environment variable or a second root. There is no reconstruction path and no "first run" amnesty.
6. **Missing is not the same as broken.** An absent history is `APPROVAL_REQUIRED` exit 14; a **present but unverifiable** history (broken hash chain, truncated tail, foreign build identity) stays the existing `PILOT_INTERNAL_ERROR` exit 18 refusal of rev 3/rev 8. Stated normatively here because item 5 alone would let a chain break be downgraded to a mere re-approval (see R-6 in 4f).
7. **Operator-guide duty (DOC).** The guide must explain **why** the approval root requires durable storage: the approval ledger is the only tamper-evident record of who approved which protected action, and on a memory-backed filesystem `fsync` succeeds while the history does not survive a reboot — the run stays fail-closed, but the audit history is lost, which is a loss of accountability, not a bypass. The compatibility matrix gains a `rootKind` column.

## 4d. OD-22-Q1 and OD-22-Q2 — arming window and redirect continuation (OWNER-11; AMENDS ADR-0042)

### 4d.1 OD-22-Q1 CONFIRMED (no design change)

Window **minimum 250 ms, default 2000 ms, maximum 10000 ms**, integer milliseconds. Out of range, non-integer, `0`, negative, `NaN` or non-numeric is a **configuration error** refused before any browser launch (`MANIFEST_INVALID` naming the JSON path from the manifest; argv refusal exit 1 from a flag). **Never silently clamp**, never "nearest valid value", never warn-and-continue. AC-086 already states this; the "pending OD-22-Q1" marker is removed from AC-086's provenance, from the traceability D7 row and from the owner packet.

### 4d.2 OD-22-Q2 — method-based redirect rules (REPLACES rev 9 3c m-22 rules 1 and 2; retains and tightens rules 3 and 4)

**APPEND to 2c.7 as item 8, replacing the rev 9 m-22 text in full.**

1. **One consumption.** The **first matching protected request** consumes the lease. Redirect continuation is tracked as part of **that consumed attempt**; no hop mints, refreshes, extends or re-arms a lease, and no hop restores a spent approval.
2. **The method is observed, never inferred.** Every hop is evaluated against the method the browser **actually uses on that hop**, as observed by the route handler (or by the SPIKE-R fallback). A status code is **never** used to assume what the method became. A hop whose method cannot be observed is **ambiguous** and fails closed (rule 6).
3. **A hop that preserves a non-GET method** must remain on the **approved normalised origin and the approved normalised path, with the approved method** — regardless of the status code that produced it, and regardless of any assumption about 307/308. Otherwise: abort, `POLICY_ROUTE_DENIED`, reason `redirect_changed_approved_target`.
4. **A 307/308 hop must preserve the approved method** and satisfy rule 3. A 307/308 that is observed to change the method is an ambiguity and fails closed.
5. **A hop that actually becomes GET** leaves the approval behind: it is evaluated through **ordinary GET route and origin policy** (manifest-allowed route for GET, allowed origin, plan binding where a plan is bound). It inherits nothing from the approval. **A GET redirect is not automatically side-effect-free and not automatically permitted**; the destructive-GET residual of 2c.11 rule 7 applies to it unchanged.
6. **Fail closed on:** lease/chain expiry, any ambiguity (unobservable method, unparseable `Location`, conflicting observations), cross-origin movement, an unexpected path change, or a method mismatch. The attempt is aborted and recorded; nothing is retried.
7. **Bounds.** Every hop must be under the configured section 7 redirect cap, **and** the whole chain under one deadline measured from the first matching request: `windowMs + 5000` ms, **absolute maximum 30000 ms**. Exceeding either aborts the chain.
8. **SPIKE-R is a GO gate (expanded).** SPIKE-R must verify **real Chromium** behaviour for **301, 302, 303, 307 and 308**: whether the route handler observes each hop at all, what method each hop actually carries, whether the body survives, and whether `route.fetch({ maxRedirects: 0 })` is required. **Implementation of rules 2–6 receives no GO before SPIKE-R reports.** If SPIKE-R finds per-hop method unobservable, the design does **not** emulate the chain silently: the attempt is aborted as ambiguous (rule 6) and the limitation is documented (see R-4 in 4f).

Added to `neg-n2-arming` as cases (k)–(r), each with its inversion: (k) 307 same target, method preserved → continues under the consumed attempt; (l) 307 to a different path → abort `redirect_changed_approved_target`; (m) 308 cross-origin → abort; (n) 303 to GET on a manifest-allowed GET route → continues as an ordinary GET; (o) 303 to GET on a route **not** allowed for GET → abort; (p) 302 observed to preserve POST → treated by rule 3, aborted unless the target is identical; (q) chain exceeds `windowMs + 5000` → abort; chain exceeds 30000 ms with a large `windowMs` → abort; (r) a hop whose method cannot be observed → abort as ambiguous, zero further hops.

## 4f. Flagged as unsound, ambiguous or underspecified in the decisions (not silently chosen)

- **R-1 (ambiguity resolved, owner may correct).** "Creates the fixture server itself **or** verifies its per-run capability" is implemented as **both**: the tests-only executable creates the server and holds the capability `start()` returned. Accepting the "or" branch alone would require a way to adopt a server created elsewhere, i.e. a registration surface — the exact defect rev 10 removes.
- **R-2 (limit of a self-check).** The executable's `argv[1]`-under-`tests/` assertion and the CLI `CI`/TTY refusals are in-process forgeable. They are documented as accident guards. The only load-bearing controls are: the authority is absent from every production require graph, it cannot be named by production construction, it has no filesystem module, and consumption is re-checked in production code.
- **R-3 (interpretation the owner should confirm).** "Not referenced by package scripts used by users" is implemented as *no package script names the executable*; it is still executed when `npm run test:regression` runs the check that spawns it, which AC-051 and AC-074 require. If the owner intends that no user-invocable script may transitively reach it, AC-051's exit-code coverage must move to a separate CI-only job, and that job becomes a new workflow surface the AC-084 check must police. **Needs confirmation before 18D.**
- **R-4 (real technical risk, SPIKE-R).** If Chromium does not expose the per-hop method, rules 2–6 cannot be enforced by observation. The design then **aborts the attempt as ambiguous** rather than emulating the chain with `route.fetch({maxRedirects:0})`, because manual continuation changes page state semantics and would make Falcon the originator of a request the browser did not make. Consequence to state: some legitimate approved POST-redirect flows would be refused. SPIKE-R must report before GO; the fallback is refusal, never a silent emulation.
- **R-5 (tmpfs permissions).** Admitting tmpfs for `run/auth` often means a shared `/tmp` mount. The existing uid-owned, `0700`, no-symlink, real-path checks must be applied to the resolved root on every pilot start; the per-root admission does not relax them. Authentication state on a shared memory filesystem is a confidentiality question distinct from the durability question the owner answered.
- **R-6 (gap closed normatively, flagged).** The decision says only that a *missing* approval history yields `APPROVAL_REQUIRED`. Read alone, that would let a **broken or truncated** chain be downgraded to a re-approval, losing the tamper-evidence refusal. Rev 10 section 4c item 6 keeps missing = exit 14 and unverifiable = exit 18. If the owner intended otherwise, say so explicitly, because the difference is the whole value of the audit chain.

Any path is a **blocker**.
3. **Redirect continuation after lease consumption (4d.2).** Does the method-observed rule close the 301/302/303/307/308 matrix; is "abort as ambiguous" the right fallback if the per-hop method is unobservable (R-4); can a GET hop reach a side effect through an allowed route; are the chain deadline and the cap jointly sufficient.
4. **tmpfs root separation (4c).** Is the per-root split sound; is the missing-versus-unverifiable history split (4c items 5 and 6) the behaviour you require; does R-5 need an added confidentiality control for an auth root on a shared memory filesystem.

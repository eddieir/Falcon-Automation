--- REPLACE rev 6 section 2b.2 rule 3 ("Admission is gated, never inferred") in full (closes M-11) ---

3. **Admission is gated, and identity is never exempt.** SEC-06 M-11 is correct: `expectRunId`/`expectCommit` are optional (`ShardMerge.js:111-112`) and `COMMON` equality runs over intact shards only, so a literal rev 6 implementation would admit a replayed or foreign refusal bundle for any shard index and let it mask that shard's failed rows as auth loss. Decision:

   a. **The expect flags are mandatory in pilot mode.** Whenever `--pilot-manifest` is given, `--expect-run-id` and `--expect-commit` are **required**. A pilot merge missing either is an **argv refusal, exit 1**, at `Runner.parseMergeExpect` (`Runner.js:47-65`) before any filesystem read — not an exit-2 input rejection, because the operator's command line is wrong, not the bundle. `--pilot-manifest` additionally yields `expectPilotManifestDigest` (the digest of the resolved, strictly loaded manifest) and `expectConfigFp`, which is derived in-process from config alone (`ParallelSweep.js:81`) and is therefore always available to the merge.
   b. **Four mandatory identity checks, applied to every bundle including a refusal bundle.** `runId`, `commit`, `configFp` and `pilotManifestDigest` are compared against the merge's own expectations for **every** shard in the set, before the intact/refusal partition. Mismatches are `UNEXPECTED_RUNID`, `UNEXPECTED_COMMIT`, `UNEXPECTED_CONFIGFP` and `MIXED_PILOTMANIFESTDIGEST`, each **exit 2**. No refusal bundle is exempt from any of the four.
   c. **Exactly two fields are exempt for a refusal shard, and only those.** `frontierDigest` and `planDigest` take the zero sentinel of 2b.2(2) because an exit-11 shard never reached discovery. Nothing else is exempt. Concretely, `COMMON` (`ShardMerge.js:35`) splits into `COMMON_IDENTITY = ["runId","commit","configFp"]`, checked over **all** shards, and `COMMON_PLAN = ["frontierDigest","planDigest"]`, checked over **intact** shards only. Rev 6's sentence "`COMMON` equality ... run over `intact` only" is replaced by this split; `buildPageTable` still runs over intact shards only.
   d. **Set-shape checks run over all shards.** `MIXED_TOTAL`, `DUPLICATE_SHARD`, `SHARD_NAME_MISMATCH`, `TOTAL_UNEXPECTED` and `MISSING_SHARD` (`ShardMerge.js:118-127`) count refusal shards as present shards. A refusal bundle therefore cannot occupy an index twice, cannot change the total, and cannot substitute for a missing shard.
   e. **Residual, explicit and unaccepted.** Bundles remain unauthenticated, so an attacker with write access to the staging directory of *this* run, at *this* commit, with *this* `configFp` and *this* manifest digest can still substitute a refusal bundle and convert that shard's exit 1 into exit 11. The exit code stays non-zero and the pages are reported `lost`, never passed; AC-023's Must property holds. Bundle signing is out of Phase 18 scope and is recorded as a residual, not a closed item.

--- REPLACE rev 6 section 2b.1(a) rule 4 ("Post-condition, asserted not assumed") in full (closes M-12, resolves unverified item 1) ---

4. **Post-condition, asserted not assumed, and ordered before any irreversible write.** SEC-06 M-12 is correct: rev 6 re-digested "after step 5", but step 4 has already appended `run_history` (`ShardMerge.js:384`) and step 5 has already written `healing_logs.json`, the report and the receipt (`:396-411`), and a receipt replay returns the stored code without recomputing it (`:286-290`). A mutation would surface as 17 once and as the stored 0/1 on every rerun. Decision:

   a. **Baseline.** The pilot merge digests `data/healing_pending.json`, `data/locator_store.json` and `data/locator_memory.json` **before** step 1 (`scenario_history`, `:317`), recording `{path, bytes, sha256}` per file, with absent treated as a declared `ABSENT` baseline rather than an error.
   b. **Check point.** The re-digest runs **after the last state step** (`locator_memory`, `:350`) and **before step 4** (`run_history`, `:384`). It is a new step named `pilot_store_check`, exposed through the existing `beforeStep` seam so tests can inject a mutation at exactly that boundary.
   c. **On mismatch, nothing downstream runs.** No `run_history` append, no `healing_logs.json`, no `exploratory_test_results.json`, no report write, and no cleanup of fragments or journals. The merge returns **exit 17** `PILOT_STORE_MUTATION`. Because no report is written, there is no PASSED report to retract; if a report from a prior run exists at `reportPath` it is **left untouched** and is not overwritten with a pilot result.
   d. **The receipt is written, and it records 17.** A refusal receipt `{schema:"falcon.merge-receipt", v:2, runId, inputDigest, code:17, reason:"PILOT_STORE_MUTATION", rankTableVersion, mergeDerivedCode, shardCodes, pilot:true, storeDigests:{before, after}}` is written **after** the mismatch is determined and is the only write that happens. Writing it is strictly safer than writing nothing: with no receipt, a replay re-reads the bundle, finds the store already mutated relative to a fresh baseline (or not), and could return 0. With the receipt, every replay returns 17.
   e. **Replay recomputes; it does not trust the stored integer** (resolves SEC-06 unverified item 1). The replay path (`:286-290`) is extended for pilot receipts only: it re-validates `schema` and `inputDigest` as today, then additionally requires `rankTableVersion` to equal the running build's table version and recomputes `argmax(rank)` over the receipt's recorded `mergeDerivedCode` and `shardCodes`. A recomputed code that differs from `code` is `RECEIPT_CODE_INCONSISTENT`, **exit 2**. A `rankTableVersion` the build does not recognise is `RECEIPT_RANK_TABLE_UNKNOWN`, **exit 2**. A `code:17` receipt short-circuits to **17** without recomputation, because 17 is a safety-invariant verdict about the local filesystem and is not derived from the rank table. A non-pilot receipt (`pilot` absent) keeps today's replay behaviour byte-for-byte, so AC-076 holds.
   f. **Receipt `v` goes to 2 for pilot receipts only.** A non-pilot merge still writes `v:1` with exactly today's key set. A `v:2` receipt read by an older build fails its `schema`/shape check and is refused, which is fail-closed.

--- APPEND a new subsection "2b.1(c) Internal worker-mode merge in pilot mode (closes m-11)" ---

SEC-06 m-11 is correct. `Runner.run` with `--workers` writes a bundle under `reports/shards/<runId>/` and then calls `runMerge({merge:{input: root, expectTotal: 1}, paths: defaultPaths(repoRoot)})` (`Runner.js:154`) with no expect flags and no `--pilot-manifest`. Under rev 6 rule 3(d) that merge would refuse its own pilot bundle, so **every pilot worker-mode run would exit 2**. Decision:

1. **The internal merge receives the in-process pilot context, not a command line.** `Runner.run` passes `ShardMerge.merge({inputDir, expectTotal:1, expectRunId: runId, expectCommit: commit, expectConfigFp: configFp, pilotManifest: <the already-validated in-process manifest object>, pilotManifestDigest: <its digest>, paths})`. The manifest is the same object the sweep ran against; it is **not** re-read from disk and **not** re-resolved, so there is no second parse and no TOCTOU window between the run and its merge.
2. **2b.1 applies to every pilot bundle in every shape.** The five-shape allowlist, the two admitted journal event types, the `timings.json` closed schema, the `pilot` manifest block, the `authContext` requirement of 2b.6, the identity checks of 2b.2(3)(b), the total rank of 2b.3 and the store post-condition of 2b.1(a)(4) apply identically to a worker-mode bundle, a shard bundle and a single-shard bundle. "Shard" in those rules means "any bundle", and the rules key off pilot mode, never off `--shard`.
3. **The argv rule of 2b.2(3)(a) is a command-line rule only.** It applies when a merge is invoked as a subcommand. The internal call is not argv, so the mandatory-flag check is expressed once, at the merge API boundary: `ShardMerge.merge` refuses `pilotManifest` present without all of `expectRunId`, `expectCommit` and `expectConfigFp` as `PILOT_EXPECT_INCOMPLETE`, **exit 2** (an internal programming error, not an operator error). The `Runner` argv path maps the same condition to exit 1 before reaching the API.
4. **Non-pilot worker mode is unchanged.** Without a pilot manifest, `Runner.js:154` passes exactly today's arguments and the merge takes exactly today's path. This is asserted by the AC-076 baseline test, which must include a `--workers` run.

--- APPEND a new subsection "2b.6 `authContext` is mandatory on every pilot fragment (closes m-13)" ---

SEC-06 m-13 is correct: rev 6 made `authContext {roleId, mode, pilotManifestDigest}` an *optional* fragment key, so a fragment that simply omits it would bypass every authentication check and could be counted as tested. Decision:

1. **Required in pilot mode.** A pilot merge refuses any fragment without an `authContext` block as `FRAGMENT_AUTHCONTEXT_MISSING`, **exit 2**, before any reducer and before the page table is built. The key stays schema-optional (so a non-pilot bundle from `2572e73` is still valid, AC-076), and the requirement is enforced by the pilot merge, exactly as the `pilot` manifest block is in rev 6 rule 3(d).
2. **Digest check.** `authContext.pilotManifestDigest` must equal the merge's own `expectPilotManifestDigest` and the owning manifest's `pilotManifestDigest`. A mismatch is `MIXED_PILOTMANIFESTDIGEST`, **exit 2**. This is per fragment, not per bundle: a bundle cannot carry fragments produced under two manifests.
3. **Role check.** `authContext.roleId` must be a declared role in the merge's own pilot manifest. An undeclared role is `FRAGMENT_ROLE_UNDECLARED`, **exit 2**. The merge compares against its own manifest, never against a role list carried in the bundle.
4. **Mode check.** `authContext.mode` is a closed enum `{"authenticated","anonymous"}`. Any other value is `FRAGMENT_AUTHMODE_INVALID`, **exit 2**. The rev 6 2b.3(4) narrowing is unchanged: an `anonymous` fragment is admitted, reported `status:"unauthenticated"`, never counted in `pagesTestedAuthenticated`, and makes a declared `exit.code` of 0 inconsistent.
5. **A refusal bundle has no fragments**, so 1–4 are vacuous for it; the identity checks of 2b.2(3)(b) are what bind a refusal bundle to its run.
6. **Non-pilot merge unchanged.** A non-pilot merge ignores `authContext` entirely and refuses a bundle that carries it under rev 6 rule 3(d).

--- APPEND to rev 6 section 2b.1(a) rule 1, write side (closes m-14, first and second parts) ---

**Write-side exit code and the no-fallback rule.** The shard process exit code for a write-side `BUNDLE_EXCLUDED_TYPE` is **17** (`safetyInvariant` in the `exitCodes` contract in `docs/phase-18-acceptance-criteria.json`), the same code as `PILOT_STORE_MUTATION`, with reason `BUNDLE_EXCLUDED_TYPE`. It is not 2: the bundle writer caught its own process emitting identity it is structurally forbidden to emit, which is an invariant violation inside the run, not a rejected external input. The run is refused and the bundle directory is removed, per rev 6 rule 1. The shard manifest admission set of 2b.3(2) is unchanged ({0,1,11,12,14}): a shard that exits 17 leaves **no** bundle, so the merge sees `MISSING_SHARD` (exit 2), never a manifest declaring 17.

**Excluded events are dropped, with no fallback write.** An event of an excluded type that is diverted from the pilot journal is **discarded in memory**. There is no fallback write to `data/`, no spill file, no `reports/` sink and no environment-variable escape hatch. In particular the diverted event must not reach `AtomicJsonStore`, `HealingTrust` or `LocatorMemory`. This is asserted by the `neg-pilot-event-divert-sink` test below, which spies on every writer and requires zero writes outside the bundle directory.

--- APPEND to rev 6 section 2b.3 as rule 7 (closes m-14, third part) ---

7. **`rank()` inputs are validated before any state write.** Rev 6 made `rank()` throw on an unranked integer, but the throw site matters: a throw after step 1 would surface through the existing non-durable path as **exit 3** with `scenario_history` already applied. Decision: every code that will be ranked — the merge-derived code and every shard-declared `exit.code` — is validated in `loadManifests`, inside the existing try block that already yields exit 2, **before step 1** (`:317`). Validation is membership in the admitted shard set {0,1,11,12,14} for a manifest code (`SHARD_CODE_NOT_ADMITTED`) and membership in the rank table for any merge-derived code (`RANK_INPUT_INVALID`); both are **exit 2**. `rank()` keeps its throw as a defence in depth, but by construction it can no longer be reached with an invalid input after a state write. The rank table carries an explicit `rankTableVersion` constant, which the receipt records and the replay of 2b.1(a)(4)(e) checks.

--- APPEND a new subsection "2b.5 Pilot healing sinks (resolves unverified item 2; corrects rev 6 2b.1(a)(5))" ---

SEC-06 asked where process-local pilot healing logs land. **Verified by grep, and rev 6 is wrong on this point:**

- `HealingReport.js:33` sets `this.filePath = path.join(__dirname, "..", "..", "..", "reports", "healing_logs.json")` — i.e. the process-local healing log is written into `reports/`, which `ci.yml:45-46` uploads as `regression-reports` and `ci.yml:342-343` uploads as `falcon-reports`. It is therefore a **persisted, uploaded artifact in AC-060 scope**, not a private file.
- `HealingTrust.js:52-53` writes `data/healing_pending.json` and `data/healing_decisions.json` directly from the run process. `data/healing_pending.json` is one of the three stores the exit-17 post-condition of 2b.1(a)(4) digests, so an in-process healer in a pilot run would mutate a protected store and could trigger a **true** 17 on a legitimate run.

Rev 6's sentence "Pilot runs record healing only in process-local logs that never enter a bundle" is correct about bundles and **misleading about artifacts**. It is replaced by:

1. **In pilot mode the healer records nothing to any shared sink.** `HealingReport` and `HealingTrust` are both disabled for the duration of a pilot run: no append to `reports/healing_logs.json`, no write to `data/healing_pending.json` or `data/healing_decisions.json`. This is a constructor/injection-time switch on pilot mode, not a per-call guard, so there is no path that forgets it.
2. **Healing still runs; only its recording changes.** Tier 1–3 healing behaviour on an authenticated page is unaffected. The cost is the OD-17-Q1 cost already recorded: no cross-run locator or healing learning from authenticated pages.
3. **Observability without identity.** A pilot run emits healing **counters only** through `Logger.info` and into the existing `timings`-adjacent run summary: attempts, successes and failures per tier, plus a refusal-reason histogram. No selector, no locator key, no locator key digest, no URL, no element text. Counters are integers and carry no application-derived identity, so they are admissible under OD-17 and cannot be a confirmation oracle.
4. **Enforcement, not convention.** The AC-060 four-location artifact scan is extended to assert that `reports/healing_logs.json` is **absent or an empty array** after a pilot run, and that `data/healing_pending.json`, `data/healing_decisions.json`, `data/locator_store.json` and `data/locator_memory.json` are byte-unchanged across the whole pilot run, not only across the merge. This is the 18A confirmation SEC-06 asked for under AC-060.
5. **If the owner answers OD-17-Q1 "yes"**, a pilot healing record returns as a sixth bundle shape with its own closed schema and its own security review, and this subsection is revised with it. It is not re-admitted by implementer discretion.

--- APPEND to rev 6 section 2b.1(b) rule 4 (closes m-12) ---

**The non-pilot path is byte-identical, with no AC-076 delta.** SEC-06 m-12 notes that `SENTINEL_DIGEST_NOT_ADMITTED` in a non-pilot merge would change non-pilot behaviour. The design takes the preferred option: **the sentinel check runs only in pilot mode.** A non-pilot merge does not test for the zero sentinel at all; a non-pilot bundle whose `frontierDigest` or `planDigest` is 64 zeros takes exactly today's path and fails today's `checkAnalysis`/`COMMON` comparisons as it does at `2572e73`. The input is unreachable for honest producers either way, so nothing is lost, and AC-076 keeps a zero-delta baseline rather than a documented exception. The same rule applies to every rev 7 refusal code: `UNEXPECTED_CONFIGFP`, `FRAGMENT_AUTHCONTEXT_MISSING`, `FRAGMENT_ROLE_UNDECLARED`, `FRAGMENT_AUTHMODE_INVALID`, `PILOT_EXPECT_INCOMPLETE`, `PILOT_STORE_MUTATION`, `RECEIPT_CODE_INCONSISTENT` and `RECEIPT_RANK_TABLE_UNKNOWN` are **pilot-mode-only** code paths. The AC-076 baseline test asserts byte-identical exit codes, reports, receipts (`v:1`, today's key set) and `timings.json` handling for a sequential run, a `--workers` run and a three-shard non-pilot run.

--- APPEND to the compatibility section ---
